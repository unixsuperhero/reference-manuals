Chapter 5 tuios manual

TUIOS: Daemon, Sessions, Remote Hosts and Compatibility Shims

How the tuios daemon holds sessions, what survives a restart, how to drive panes from a shell, how sessions reach other machines, and the tmux and herdr compatibility layers.

tuiossessionsdaemonremotecli

A plain tuios does not run your shells itself. It starts (or finds) a background daemon that owns every shell, every terminal emulator and every session, and then attaches a client that only draws what the daemon holds and forwards your keys. This chapter covers that split end to end: running and debugging the daemon, creating and attaching sessions, what comes back after a restart, driving panes from an ordinary shell or script, reaching sessions and panes on other machines, serving tuios over SSH and the web, and the tmux and herdr compatibility layers that let tools written for other multiplexers work inside tuios.

The agent-specific half of the pane interface (reporting state, mail, the Inbox, approvals, fleets) is in Agents. The full option reference is in Configuration, and every command’s flags are in the CLI reference.

Ctrl+B is the default leader key and is used throughout. It is configurable with leader_key; see Keybindings.

Local sessions and daemon sessions

tuios runs in one of two modes.

Mode Started by Where the shells live Survives the client Saved to disk
Daemon session tuios, tuios new, tuios attach A separate tuios daemon process Yes Yes
Local (standalone) session tuios --standalone, TUIOS_NO_DAEMON=1, startup.daemon = false The tuios process you started No No

A local session keeps the window manager, the terminal emulators and the shell processes inside one process. No daemon starts, no socket is created and nothing is written to disk. When the process exits, for any reason, the session is gone. It is the right choice when you want a window manager for the life of one terminal window, and it is the way back to a terminal when the daemon is the thing that will not start.

tuios --standalone           # this one run
TUIOS_NO_DAEMON=1 tuios      # every tuios started from this shell
[startup]
daemon = false               # every tuios, from the config file

The flag and the environment variable both beat the config file.

A daemon session lives in the daemon. The daemon owns the shell processes (PTYs) and runs a terminal emulator for each one, so output keeps being parsed whether or not anyone is watching. A client subscribes to PTY output, draws it, and forwards your keystrokes back. Everything else in this chapter is about daemon sessions.

startup.daemon ships true, so a bare tuios attaches to a daemon session. If the daemon will not start, tuios says so and runs that one session standalone rather than leaving you without a terminal. The [startup] booleans are read only from the config file, so an install that already has a config file keeps doing what that file says.

The daemon

Starting it

You rarely start the daemon by hand. tuios, tuios new, tuios attach and tuios resurrect all start it when no daemon answers on the socket. When it starts, it restores every session it finds saved state for (see Restarts and resurrection).

Three explicit ways exist:

tuios daemon                       # run in the foreground, logs to the terminal ring
tuios daemon --log-level=messages  # foreground, with protocol messages logged
tuios daemon --no-restore          # do not restore saved sessions on start
tuios start-server                 # start it in the background and return

tuios daemon is the debugging form: it runs in the foreground until you stop it. tuios start-server is a hidden command (it is not in tuios --help) that starts the daemon in the background and restores saved sessions without taking over the terminal, which is what a script wants.

Flag of tuios daemon Meaning
--log-level off, errors, basic, messages, verbose or trace
--no-restore Leave saved sessions on disk instead of restoring them; tuios resurrect NAME restores one on demand

Stopping it

tuios kill-server

kill-server stops every session and disconnects every client. It is synchronous: it returns only after the daemon has written every session’s state and removed its socket, so a new daemon can start the moment it returns. It fails if the daemon has not finished within 10 seconds.

kill-server ends every program running in every pane. The layouts, window names, working directories and pane history are saved and come back on the next start, but with new shells. A vim, a build or a running agent turn is gone.

SIGTERM and SIGINT save cleanly too; SIGKILL does not (What survives).

Where the daemon lives on disk

What Path
Daemon socket $XDG_RUNTIME_DIR/tuios/tuios.sock, falling back to /tmp/tuios-<uid>/tuios.sock (%LOCALAPPDATA%\tuios\tuios.sock on Windows)
Daemon PID file The socket path with .pid appended
herdr protocol socket The socket path with .herdr appended
tmux shim files tmux/ beside the socket: tmux/bin/tmux, tmux/socket, tmux/buffers/, tmux/p/
Saved session state $XDG_STATE_HOME/tuios/sessions/<name>.json
Saved pane history $XDG_STATE_HOME/tuios/sessions/scrollback/<session>/
Archived bad state $XDG_STATE_HOME/tuios/sessions/archive/, pruned after 14 days

tmux shim log $XDG_STATE_HOME/tuios/tmux-shim.log

When XDG_STATE_HOME is unset, the state directory is the platform’s default: ~/.local/state/tuios on Linux and ~/Library/Application Support/tuios on macOS.

The socket is in the runtime directory and does not survive a reboot, which is correct, because the daemon does not either. Saved state is in the state directory and does survive, which is why a session can be resurrected after a reboot.

XDG_RUNTIME_DIR chooses the daemon; TUIOS_SOCKET does not

Every tuios command reaches the daemon whose socket is under XDG_RUNTIME_DIR (on Windows, LOCALAPPDATA). That is the only selector.

TUIOS_SOCKET is the other direction: tuios sets it in every pane to the socket of the daemon that runs the pane, so a program can tell which daemon it belongs to, and every process started from the pane inherits it. A command compares the two:

  • TUIOS_SOCKET unset, or naming the socket the command is about to use: the command runs.
  • TUIOS_SOCKET naming another socket where a daemon is listening (for example a script in a pane that set its own XDG_RUNTIME_DIR): the command runs against the daemon XDG_RUNTIME_DIR names.
  • TUIOS_SOCKET naming a socket where nothing listens: the command refuses, because that is someone expecting the variable to select a daemon.
TUIOS_SOCKET is set to /tmp/old/tuios/tuios.sock, where no daemon is listening,
and this command would use the daemon at /tmp/tuios-501/tuios.sock instead.
TUIOS_SOCKET only reports the daemon a pane belongs to; it does not choose one.
To use a separate daemon, set XDG_RUNTIME_DIR (LOCALAPPDATA on Windows) and
XDG_STATE_HOME, so it keeps its own saved sessions, to directories of your own;
its socket is then $XDG_RUNTIME_DIR/tuios/tuios.sock. Otherwise unset TUIOS_SOCKET

The one reader that connects to TUIOS_SOCKET directly is tuios mcp; see Agents.

A throwaway daemon

For a test, a demo or a script that must not touch your real sessions, give a second daemon its own runtime directory and its own state directory. The runtime directory gives it its own socket; the state directory keeps its saved sessions apart from yours.

export XDG_RUNTIME_DIR=/tmp/scratch/run XDG_STATE_HOME=/tmp/scratch/state
mkdir -p "$XDG_RUNTIME_DIR" && chmod 700 "$XDG_RUNTIME_DIR"
tuios new scratch --detach      # starts a daemon at /tmp/scratch/run/tuios/tuios.sock
tuios ls                        # that daemon's sessions only
tuios new-window -s scratch build --cwd ~/src/api
tuios kill-server               # stops it; your real daemon is untouched
rm -rf /tmp/scratch

Set both variables. With only XDG_RUNTIME_DIR, the second daemon writes its saved sessions into the same state directory as your real daemon, and the two see each other’s saved sessions on their next start.

Logs

The daemon keeps its recent log entries in a ring buffer of 1000 entries. tuios logs reads it:

tuios logs              # the last 50 entries
tuios logs -n 100       # the last 100
tuios logs --all        # everything in the ring
tuios logs -f           # follow new entries
tuios logs --clear      # print, then empty the ring

The ring lives in the daemon and dies with it, so the daemon also appends errors and basic events to $XDG_STATE_HOME/tuios/daemon.log. A crash leaves a record there.

Level What it records
off No debug output (default)
errors Only errors
basic Connection events and errors
messages Every protocol message except PTY input and output
verbose Every message, PTY input and output included
trace Full payload hex dumps

Raise the level of a running daemon without a restart, or set it before it starts:

tuios set-config daemon.log_level messages   # applied at once
TUIOS_LOG_LEVEL=basic tuios daemon           # wins over daemon.log_level; 0-5 also accepted

verbose and trace record pane content, window titles and paths. Turn them off when you have the trace you need.

tuios doctor

tuios doctor checks parts of tuios that are set up outside the daemon. In v0.8.5 it has two checks; it is not a daemon health check (use tuios ls and tuios hosts for that).

Command What it reports

tuios doctor agents For each harness, whether its tuios integration is installed and current (see Agents)

Upgrades and a daemon older than the CLI

After you upgrade the binary, the old daemon keeps running and serving the socket. tuios update says so when it finishes: “The daemon keeps running the old build until it is restarted.” If the old daemon cannot speak the new CLI’s control protocol, every command fails the same way:

The running TUIOS daemon does not speak this CLI's control protocol (daemon 0.9.0, CLI 1.4.0).
Most likely cause: TUIOS was upgraded while the daemon kept running, so the old daemon is still serving the socket.
Fix: run 'tuios kill-server', then run this command again.

The fix is a restart: tuios kill-server, then tuios (or tuios attach). Sessions come back as described in Restarts and resurrection. tuios-web beside tuios is updated at the same time, because the two talk to one daemon and it compares their versions.

When the daemon is not running

The CLI distinguishes three situations:

Message says What it means Fix
“is not running” No socket exists. The daemon never ran, or was stopped tuios new, tuios attach or tuios start-server
“a stale socket is left over at …” The daemon crashed without cleaning up tuios kill-server, which removes it
“Permission denied … socket” The socket belongs to another user, or its mode changed ls -l the path; set XDG_RUNTIME_DIR to a directory you own

tuios ls tells a script which situation it is in by its exit code: 0 is a running daemon (even one with no sessions), 3 is no daemon, 1 is a failure. With no daemon, the sessions saved on disk are listed anyway, marked saved:

tuios ls >/dev/null 2>&1
case $? in
  0) echo "daemon running" ;;
  3) echo "no daemon; saved sessions listed"; tuios start-server ;;
  *) echo "tuios ls failed" ;;
esac
saved: on disk only, with no daemon running to hold it.

Sessions

A session is a named set of windows, grouped into numbered workspaces, held by the daemon. It has a name (what you type with -s, attach and kill-session), a stable id (a uuid that survives renames and restarts), and optionally a label and an accent that change only how it looks.

The session lifecycle at a glance

// One session, as `tuios ls --json` reports it (trimmed)
{
  name: "work",                 // what -s, attach and kill-session take
  id: "9ef60c92-1a22-45bd-9778-2ee2fb00f905",  // survives rename and restore
  created: 1791306553,          // unix seconds
  last_active: 1791367131,
  window_count: 4,
  attached: true,               // at least one client is drawing it
  width: 280, height: 63,       // the session's size
  windows: [
    { id: "36220082-...", title: "api tests", workspace: 2,
      foreground_cmd: "go", agent_state: "none" },
    // ...
  ]
}

Creating a session: tuios new

tuios new                      # a session with a generated name, attached
tuios new work                 # a session named work, attached
tuios new ci --detach          # create it headless and return
tuios new work --theme dracula # appearance flags of the root command apply
tuios new deploy --global      # a global session (see Remote hosts)
tuios new --host build         # create it on the machine "build" and attach
tuios new --host build ci -d   # create it on build and return

tuios new starts the daemon if needed, creates the session and attaches to it. With --detach (-d) the session is created with no client: it gets an initial window and is immediately usable by control commands such as send-text, capture-pane and run-command. Attach to it later.

Flag Meaning
-d, --detach Create the session headless, with no client attached
--global Create a global session, which holds panes from more than one machine
--host NAME Create the session on a host from the [hosts] table
--ssh With --host, run ssh to the host and its own tuios instead of attaching here
--hold After a failure, wait for Enter before exiting

A name the daemon already holds is refused with session_exists, which lists the names that do exist. Choose another name rather than assuming you took the existing session over.

Attaching: tuios attach

tuios attach                   # the most recent session
tuios attach work              # a named session
tuios attach work -c           # create it if it does not exist
tuios attach --host build api  # the session api on the machine build
tuios attach work --terminal-mode   # start in terminal mode for this attach

If the daemon is not running, attach starts it, which restores every session saved on disk, and then opens one of those. With nothing saved and no name given, a new session is opened instead. A name that matches no session is an error unless -c is given.

Flag Meaning
-c, --create Create the session if it does not exist
--force Attach even from a pane of the same session
--host NAME Attach a session on a host from the [hosts] table
--ssh With --host, run ssh to the host and attach with its tuios, nested in this client
--terminal-mode Start in terminal mode, whatever startup.start_in_terminal_mode says
--hold After a failure, wait for Enter before exiting

attach, new and resurrect check the terminal before taking over the screen. They refuse when it is smaller than 40x12, when TERM is unset or dumb, or when stdout is not a terminal. For non-interactive use, drive the session with the commands in Driving panes from a shell instead of attaching.

Attaching from inside a pane

Attaching to the session you are already in would draw tuios inside itself. The attach is refused and says what to do:

You are inside session "work". Attaching to "work" here would show tuios inside itself.
Open a new terminal outside tuios to attach to it. To attach anyway, run 'tuios attach --force work'.

An unnamed tuios attach from a pane is refused with a pointer to tuios attach NAME and tuios new NAME. Attaching a different session from a pane works and nests that session’s client in the pane. --force (or TUIOS_ALLOW_NESTED=1 in the environment) lets the self-attach through.

Detaching, quitting and terminal mode

Key Effect in a daemon session
Ctrl+b d Detach. The client pushes its state to the daemon and quits. The session, its windows and its shells keep running
Ctrl+b q Quit. Kills the session, on the reasoning that quitting says the session is over. A confirmation appears first if a window runs a foreground process (confirm_quit = true always asks)
Ctrl+b Esc, Alt+Esc Leave terminal mode for window mode. A bare Esc goes to the program

Ctrl+b q is not detach. In a daemon session it kills the session and deletes its saved state, the same as tuios kill-session. Use Ctrl+b d to leave a session running.

A client that dies without detaching (its terminal closed, the SSH connection dropped, the process killed) is a detach as far as the session is concerned. The daemon notices the connection go and keeps the session running. Nothing is lost, because nothing the session needs lived in the client.

When the session is killed while you are attached, the client exits non-zero and says so instead of leaving you in a dead screen:

Session "work" was terminated while you were attached.

When the daemon itself goes away, the client reports a lost connection.

Session size with more than one client

Any number of clients may attach to one session at once, from local terminals, the SSH server and tuios-web. Each sees the same windows and output, and state changes (a window opened, moved or closed, a workspace switched) are broadcast to every client as they happen.

Every attached client has full control: it sees all output, sends input and manages windows. There is no per-client permission tier. Local clients are gated by the socket’s Unix permissions (same user), SSH clients by SSH authentication, and web clients by what stands in front of tuios-web. Share a session only with someone you would hand the keyboard to.

A pane has one size, so a session has one size for all of its clients. daemon.window_size chooses which client sets it, using the values of tmux’s window-size option:

Value The session takes the size of What a different-sized client sees
smallest (default) The smallest client The full session, with empty space around it on a larger client
largest The largest client A smaller client shows the part of the session around the cursor
latest The client that last had input Same as largest for every client but the latest

How latest decides:

  • Input is a key, a paste, a click, a drag or a turn of the mouse wheel. A resize, a focus change and a reply your terminal sends by itself (a colour reply) are not input. tmux counts resizes and focus changes; tuios does not, so a phone that only attaches does not take the session from the person typing on a laptop.
  • A client keeps the session for 1 second after its last input, so two people typing at once do not resize the session on every key.
  • The first client to attach sets the size until another client has input. When the latest client detaches, the size goes to the client with the most recent input.

A client smaller than the session shows the part around the focused pane’s cursor (an agent CLI leaves its cursor in its input box, so you see that), and a mark above the dock shows the session’s size.

A client that cannot send input, such as tuios-web --read-only, does not set the size under largest or latest. A tool that uses only the verb socket (a script, Collie) is not a client with a size at all.

tuios set-config daemon.window_size latest -s work      # this session, now
tuios session-info -s work --json | jq '{window_size, session_width, session_height}'
tmux set -g window-size latest                          # the same, under the tmux shim

Session information

tuios session-info -s work
tuios session-info -s work --json | jq -r '.tiling_mode'

session-info reports the current workspace, the tiling mode, the size, the window size policy, any workspace names and, when workspaces were rearranged, their display order. Workspaces keep their numbers, so select-workspace 2 still means workspace 2.

Switching sessions inside the app

Ctrl+b S opens the session switcher.

Key Action
typing Fuzzy-filter the list
Enter Switch to the highlighted session; with no match, create a session with the typed name and switch to it
Ctrl+r Rename the highlighted session
Ctrl+d Delete the highlighted session, after a confirmation. Never the one you are on

Switching is not detach and reattach: the client tears down its view of the current session and builds a view of the target in place. The session you left keeps running. The rail, the command palette and session cycling switch the same way. With remote hosts configured, the switcher also lists their sessions as name @ host; rename and delete work only on sessions on the machine you are on.

Renaming a session

tuios rename-session test work     # rename "test" to "work"
tuios rename-session work          # rename the session of this pane (or -s)

The rename changes the session’s name in the daemon, so tuios ls, tuios attach, -s and every client use the new name, and new panes get it as TUIOS_SESSION. Panes that already run keep the old name in TUIOS_SESSION, and tuios commands from them still reach the session. tuios attach and tuios kill-session with the old name fail and name the new one. An event stream on the session keeps going under the new name. A name another live or saved session has is refused. A renamed session keeps its saved history files.

Labels and accents

A label is a display name: it shows in the sidebar and the dock, and the session keeps its own name for addressing, persistence and TUIOS_SESSION. Scripts that target the session by name keep working.

tuios set-session-name "Payments API"          # label the current session
tuios set-session-name -s work "Payments API"  # label a named session
tuios set-session-name                         # clear the label
tuios set-session-accent cyan                  # the session's accent colour
tuios set-session-accent                       # clear it

The accent is shared by every attached client and survives a reattach. Each session also gets its own colour on the rail and in the switcher unless appearance.session_colors = false; appearance.session_border = true carries it onto every pane border. See Configuration.

Killing a session

tuios kill-session work

kill-session closes every window in the session, ends their processes and disconnects attached clients. It also deletes the session’s saved state and history, because an explicit kill is a deliberate teardown and must not leave the session restorable. Quitting from inside the client (Ctrl+b q) does the same.

The scratch terminal and picture in picture

Two features live beside sessions without being sessions. The scratch terminal (Ctrl+b g, sized by [scratch]) is a small layout of panes per session, shown in a box over the current workspace; its shells keep running while hidden and it survives detach, and after a restart it comes back hidden with new shells. list-windows --json shows its panes with "scratch": true and a workspace number of 1000 or more. Picture in picture (tuios pip -s work agent, tuios pip --off, sized by [pip]) pins a live copy of one pane in a corner; it belongs to the client, so a detach forgets it. An old scratch session left by an earlier version can be removed with tuios kill-session scratch. Both are covered in Keybindings.

Restarts and resurrection

What survives

There are four kinds of interruption. “Structure” means the window count, geometry, workspace assignment, custom names, minimize state, the BSP tree and the layout mode.

Client exits (detach, crash, SSH drop) Daemon restart (kill-server, SIGTERM) Daemon crash (SIGKILL, OOM) Reboot
Session exists afterwards Yes Yes, restored on daemon start Yes, restored on daemon start Yes, restored on daemon start
Session id Yes Yes Yes Yes
Window structure Yes Yes As of the last save, a couple of seconds stale As of the last save
Shell processes Yes, they keep running No, fresh shells No, fresh shells No, fresh shells
Working directories Yes Yes, on Linux and macOS The cwd from the last save The cwd from the last save
Screen contents Yes Yes, as history above a divider As of the pane’s last save, up to 30 s stale Yes, as for a restart
Scrollback Yes Yes, the last 1000 lines by default As of the pane’s last save Yes, as for a restart
Running programs (vim, tail, a build) Yes No No No
Agent conversations Yes, the agent keeps running The conversation, not the process Same Same
Copy-mode position, selection No, per client No No No
Input mode (window or terminal) No, per client No No No

The first column is the important one: a detach costs nothing, because the daemon holds the PTYs and keeps an emulator fed for each. On reattach the client asks the daemon for each window’s screen and scrollback and repaints it. Copy-mode state and input mode are deliberately per client, so that one client entering terminal mode does not change what another client is doing.

The three daemon columns are all resurrection: nothing survives a daemon exit except what was written to disk.

When state is saved

Each live session writes its state to $XDG_STATE_HOME/tuios/sessions/<name>.json:

  • within a couple of seconds of any change to its structure;
  • every 30 seconds whether or not anything changed, which is how each window’s working directory stays current (a cd changes no structure);
  • once more on a clean shutdown (kill-server, SIGTERM, SIGINT), while the shells are still alive, so the directories in it are accurate.

The write is atomic (a temp file renamed into place), so a crash mid-write cannot leave a half-written file. The file holds the structure: windows with geometry, titles, custom names, workspace, minimize state, focus, BSP trees, layout mode, each window’s working directory, the session id and, for an agent pane whose harness reported it, the conversation id. It holds nothing about the processes.

Working-directory capture reads /proc/<pid>/cwd on Linux and proc_pidinfo on macOS. On Windows and the BSDs there is no answer, and a restored shell starts in its default directory. Everything else about the restore works.

What a restore looks like

When the daemon starts, it restores every session it has saved state for (unless it was started with --no-restore). For each window it spawns a fresh shell in the saved working directory (or the shell’s default directory if the path is gone) and writes a dim one-line notice into it:

-- tuios: session restored, fresh shell in /home/you/project --

When the pane has saved history, the notice is a divider under that history:

$ make
...the last lines of the build...
$
-- tuios: restored from Sep 30 14:02, fresh shell in /home/you/project --
$ _

The session is marked as well. It shows a restored tag in tuios ls, the sidebar and the switcher, and the first tuios attach says so before it hands over the screen:

Session "work" was restored: layout came back from saved state; the shells are new.

The mark is cleared by that first attach and does not come back unless the daemon restores the session again.

Restored shells use the daemon’s environment. No client is connected at restore time, so the shell comes from the daemon’s $SHELL and inherits the daemon’s environment, not the environment of the terminal you later attach from.

TUIOS_RESTORED

A restored shell has TUIOS_RESTORED=1 in its environment, so your shell startup file can react to a restore without parsing the banner.

# ~/.zshrc
if [ "$TUIOS_RESTORED" = "1" ]; then
  print -P "%F{yellow}restored pane in $PWD; last session's output is above%f"
fi

A script that holds window ids and names can keep using them: a restored session keeps its names, workspace names, window ids and window names. Mail and agent state died with the old daemon. Treat a restored session as panes to be started again, addressed by the ids and names you already know.

Pane history (scrollback persistence)

The daemon saves each pane’s history next to the session’s state file, and a restore shows it again as text to read. It is not replayed into the new shell, and no command in it runs again.

What comes back is the scrollback, up to persist_scrollback_lines (1000 by default), and the screen the pane showed, with colours, styles, wide characters and wrapped lines intact. With a full-screen program open, the shell’s screen beneath it comes back, not the program’s. The scratch terminal’s history is saved; other popups are not.

When it is saved: on a clean stop for every pane with new output, and during the session with the periodic save, at most once per pane every 30 seconds. An idle pane is not written again. After a crash a pane comes back with history up to 30 seconds old.

Limit Value
Directory $XDG_STATE_HOME/tuios/sessions/scrollback/<session>/, mode 0700
One file per pane Compressed, mode 0600, at most persist_scrollback_kb (2048 KiB)
All files of one session At most 16 MiB together; a pane that does not fit saves fewer lines
Deleted when The pane closes, the session is killed, or the daemon starts and finds history with no saved session

A pane that ran on another machine through [hosts] comes back as a local shell without history; that machine keeps its own copy.

Privacy. The history files hold whatever your panes printed, which can include passwords and tokens. Set persist_scrollback = false in [daemon] to stop saving it. The next time the daemon starts, it deletes what it saved before.

Agents after a restart

An agent’s process ends like any other, and the turn it was running does not finish. A coding agent keeps its conversation on disk, though, and a pane whose harness reported the conversation id keeps that id in the state file. On restore, daemon.resume_agents decides what happens:

Value Effect
ask (default) A Resume row appears in the Inbox; answer it with y
auto The harness’s resume command (claude --resume <id> or its own form) is typed into the new shell
off Neither

tuios resume-agent -w PANE does it by hand. See Agents for the harness wiring that records conversation ids.

The resurrect command

tuios resurrect              # list the sessions that can be restored
tuios resurrect work         # restore that session and attach to it
tuios restore work           # alias

With no arguments, resurrect prints every saved session with its window count, whether it is already live and how long ago it was saved. With a name, it starts the daemon if necessary, restores that session from saved state and attaches. It is a no-op restore when the daemon already restored the session on start, in which case you attach to the live one. It is the way to bring back a session when the daemon ran with --no-restore.

If a restore fails, the command says which reason applies: there is no saved state under that name, the state is corrupt, or the state was written by a newer tuios. In the last two cases the file was moved into sessions/archive/ (not deleted) and the message prints where. One bad file never blocks the daemon from starting or other sessions from restoring.

Example: a planned daemon restart

tuios ls                     # note what is running
tuios kill-server            # saves every session, then exits
tuios start-server           # restores them in the background
tuios ls                     # each restored session carries the "restored" tag
tuios attach work            # prints the restored notice, then attaches

Rehydration: how a client fills a pane

Rehydration is the internal contract for how a client comes to hold a pane’s content; it is why a workspace switch, a reattach and a second client all show exactly what the pane holds. The daemon’s emulator is authoritative, since it has seen every byte. A client applies a snapshot of it (grid, the screen under an alternate screen, cursor, pen, modes, scroll region, character sets, kitty keyboard stack and up to 1000 scrollback rows, tagged with a stream position), and the live stream (a 64 KB ring per PTY) resumes exactly where the snapshot ends, so nothing is painted twice. A client that already holds history only ever gains lines. The contract and its tests are in REHYDRATION.md.

Driving panes from a shell

Everything a person does with keys has a command, and every command talks to the daemon over its socket. So the same commands work from inside a pane, from a plain shell outside tuios, from cron and from a script, whether or not a client is attached. This section is the shell-side interface. Agents use the same commands plus the state, mail and Inbox commands in Agents.

What a pane may do

tuios pane-grants
Pane 98db8226 in session work holds admin (the default of [agents.permissions], mode open).

The grants are read, write, fan, respond and admin. Under the default mode open a pane holds admin, so every script works. Under strict a pane holds read, write and fan unless the person set others. A call your grants do not cover fails with forbidden, changes nothing and names the grant it needed. new-window --grants opens a pane with fewer grants. The model is in Agents.

Addressing sessions and windows

Sessions take -s NAME. Omit it and the most recently active session is used, which is a guess when several are live. Inside a pane, pass -s "$TUIOS_SESSION". A few commands (close-workspace, xpanes, rename-session) default to the pane’s own session instead.

Windows take -w TARGET, resolved in this order:

Order Form Example Notes
1 Full uuid -w 98db8226-1829-468e-89a8-41a2baa0ddab Always exact
2 Index -w 3 The number list-windows prints. All digits. Shifts when an earlier window closes
3 Exact name -w build A name you gave (new-window build, set-window --name), before a program’s title
4 Unique id prefix -w 98db Ambiguous prefixes are an error

A name wins over a prefix, so a pane called db is never mistaken for a pane whose id starts with db. An ambiguous name or prefix is an error that lists what it matched, never a guess. Because the index shifts, a script should hold the id or the name.

Other machines use HOST:SESSION for -s and HOST:SESSION:WINDOW for -w; see Addressing another machine.

tuios list-windows -s work               # index, id, name, workspace, focus
tuios list-windows -s work --json | jq -r '.windows[] | "\(.index)\t\(.window_id)\t\(.title)"'
tuios get-window -s work build           # one window in detail

For a pane whose shell marks its commands, list-windows --json also reports at_prompt, command_seq, last_exit_code and last_cmdline.

A session of your own

To set up a workspace rather than drive one that exists, create the session first. It runs detached until someone attaches.

tuios new scratch --detach
tuios new-window -s scratch build --cwd ~/src/api

{"id":1,"verb":"new-session","params":{"name":"scratch","window_name":"build","cwd":"/src/api"}}

Typing text: send-text

tuios send-text -s work -w build 'go test ./... 2>&1 | tee /tmp/test.log
'
tuios send-text -s work -w build 'partial input'          # typed, not submitted
printf 'go build ./...\n' | xargs -0 tuios send-text -w build

send-text writes the argument to the pane’s PTY with no key parsing at all: spaces, quotes and punctuation arrive as typed. End the text with a newline to run it. This is the command for text.

Text sent to a pane running an agent is read as if a person typed it, and text sent to an agent waiting on a prompt answers that prompt. To talk to an agent use ask-agent or mail; see Agents.

Sending keys: send-keys

send-keys sends named keys: arrows, page keys, Enter, Ctrl+c. It splits its argument on spaces and commas and maps each token to a key, so it cannot type text:

tuios send-keys -s work -w build ctrl+c            # interrupt
tuios send-keys -s work -w docs Down --repeat 10   # scroll a pager
tuios send-keys -s work -w docs 'PageDown PageDown'
tuios send-keys -s work -w docs q
tuios send-keys -s work -w docs '\e[B'             # a raw escape sequence
tuios send-keys -s work -w build 'echo hello'      # WRONG: types "echohello"
sent 10 keys to window docs (3a42ab8f)

With -w the keys go to that window’s terminal, attached or not and whichever window has the focus. Without -w they go to the attached client as the person’s keys: the focused window, or the window manager in window mode (with no client attached, to the focused window). Always pass -w unless you mean to press keys for the person.

Waiting instead of polling: wait-for

The daemon watches its own events, so a script never needs a capture-pane-and-sleep loop. wait-for blocks until a condition matches, exits 0, and otherwise exits non-zero with the timeout error.

tuios wait-for window-output    -s work -w build --pattern 'ok\s+github' --timeout 120000
tuios wait-for window-idle      -s work -w build --idle 2000
tuios wait-for window-exit      -s work -w build --timeout 600000
tuios wait-for session-exists   -s work
tuios wait-for command-finished -s work -w build --timeout 600000
tuios wait-for command-finished -s work -w build --command-seq 4
tuios wait-for agent-state      -s work --until needs_input
tuios wait-for agent-message    -s work -w "$TUIOS_PANE_ID" --timeout 600000
Condition Matches when
session-exists The named session is present
window-output The window printed something matching --pattern, a Go regular expression, searched over the scrollback too
window-idle The window printed nothing for --idle ms (default 500)
window-exit The window’s process exited
command-finished A shell that sends OSC 133 marks finished its next command (or, with --command-seq N, the first after N; matches at once if that already happened). Prints the exit code
agent-state An agent reached one of the --until states (Agents)
agent-message Mail arrived (Agents)

Markers: the one trap in window-output

window-output matches the whole scrollback, including text that was there before you started waiting. The pane echoes the command you typed, so a marker written literally in the command matches its own echo at once, and a fixed marker from an earlier run matches again. Make the marker fresh and let the pane assemble it:

n=$(date +%s)
tuios send-text -s work -w build "go test ./... ; printf 'tests_done_%s\n' $n
"
tuios wait-for window-output -s work -w build --pattern "tests_done_$n" --timeout 300000
tuios capture-pane -s work -w build --scrollback --lines 60

The echo shows printf 'tests_done_%s\n' 1786700000, which the pattern does not match; the output shows tests_done_1786700000, which it does.

Exit codes without shell integration

Put the status in the marker:

n=$(date +%s)
tuios send-text -s work -w build "go test ./... ; printf 'done_%s_rc=%s\n' $n \$?
"
tuios wait-for window-output -s work -w build --pattern "done_${n}_rc=" --timeout 300000
rc=$(tuios capture-pane -s work -w build --scrollback --lines 60 | grep -o "done_${n}_rc=[0-9]*" | tail -1)
echo "${rc##*=}"

Or run the work in a window that exits, and wait for the exit:

tuios new-window -s work job --no-focus
tuios send-text -s work -w job 'go test ./... > /tmp/test.log 2>&1; exit
'
tuios wait-for window-exit -s work -w job --timeout 300000
tail -60 /tmp/test.log

Running a command and getting its exit code: run

tuios run -s work -w build --timeout 600000 -- go test ./... && echo passed

Arranging panes with verbs

Every arrangement has a verb that works attached or detached, does not depend on the person’s keymap, and reports what changed:

tuios focus-window -s work build               # focus a named pane, on any workspace
tuios move-window -s work 2 -w build --follow  # send a pane to workspace 2
tuios select-workspace -s work 2
tuios set-window -s work -w build --name "api tests" # also --minimize, --restore

Geometry belongs to the attached client, so these need one and fail with needs_client when none is attached:

tuios split-window -s work vertical -w build --name logs
tuios set-layout -s work --tiling true --equalize
tuios focus-window -s work --direction left

Reading, writing, waiting, creating and moving never need a client. A keybinding with no verb of its own is reachable by name with tuios run-command -s work ToggleZoom (--list prints the names); it reports that the command ran and nothing about what changed, so prefer a verb.

Popups

tuios popup runs one command in a floating pane centred over the layout. It closes when the command exits, is not tiled, is not in the window cycle and cannot be minimized. It needs an attached client.

tuios popup -s work --width 60 --height 20 -- gum choose one two three
file=$(tuios popup -s work --capture-stdout -- fzf)
tuios popup -s work --wait -- gum confirm "Deploy?" && ./deploy.sh
tuios popup -s work --width 90% --height 80% -- htop
tuios popup -- sh -c 'tuios send-text -w main "$(ls | fzf)"'
tuios popup --json -- fzf | jq -r .window_id
Flag Default Meaning
--width 80% Cells or percent of the pane region
--height 60% Cells or percent
--wait Stay until the command exits, and exit with its status
--capture-stdout Print the command’s stdout here (implies --wait; not on Windows)
--timeout while open With --wait, milliseconds to wait
--cwd, --name, --workspace Directory, name and workspace

The popup draws on its own screen, not this command’s output. A picker such as fzf or gum draws on the terminal and prints only the choice, so with --capture-stdout the choice is what tuios popup prints. A popup closed by hand exits 130. Example: a build-and-notify script run from any shell

#!/bin/sh
set -e

tuios wait-for session-exists -s "$s" --timeout 5000 || tuios new "$s" --detach

tuios wait-for window-idle -s "$s" -w "$id" --idle 500
if tuios run -s "$s" -w "$id" --timeout 900000 --lines 30 -- make test; then
  tuios run-command -s "$s" CloseWindow "$id"
else
  tuios popup -s "$s" --wait -- sh -c 'echo "tests failed; see the ci pane"; read _' || true

Remote hosts

tuios can reach other machines you name. The daemon holds one ssh link to each machine in the [hosts] table, and sessions, panes, agents, mail and the Inbox reach across it. There are three distinct things to keep apart:

You want Use Where the session lives Where the process runs
To work in a session on another machine tuios attach --host build api, tuios new --host build build build
One pane on another machine inside a local session tuios new-window NAME --host build here build
A session whose panes span machines tuios new NAME --global here (held by this daemon) each pane on the machine you pick

The machinery is the federation layer (internal/federation): a link per host, dialled by ssh with BatchMode on, carrying the daemon’s control protocol as framed streams. Nothing is discovered on its own: a host exists because you named it, and names are matched exactly, never guessed.

Adding and checking hosts

tuios hosts add build gaurav@buildbox                    # user@host
tuios hosts add work workstation                         # an ssh_config alias
tuios hosts add build gaurav@buildbox --command /opt/tools/tuios
tuios hosts add lab lab-01 --ssh-option -J --ssh-option bastion
tuios hosts add build gaurav@buildbox --repos-root '~/src' --connect-timeout 5
tuios hosts test build                                   # dial once, say what happened
tuios hosts                                              # every host and its link state
tuios hosts --json
tuios hosts remove build

hosts add writes the [hosts] table and the running daemon follows the file, so no restart is needed (from inside a pane, a change that gives a machine more waits for tuios config apply from a terminal outside tuios, or a restart). The link is tested at once for a few seconds and the result printed; a host that does not answer is still added.

The link finds tuios on the host by itself: on the PATH, then at the known install paths, then in a login shell. --command names a binary instead. tuios hosts test runs ssh itself (no daemon needed), prints the binary it found, or prints what ssh said (“Permission denied”, “Host key verification failed”) and every place it looked.

Links run ssh with BatchMode on, so a link never asks for a password or about a host key. Run ssh to each machine once by hand to accept its key, and use key authentication. TUIOS_SSH names another ssh program, for the daemon’s links (set it where the daemon starts), --ssh and hosts test.

Attaching a session on another machine

tuios attach --host build api     # attach the session api on build
tuios new --host build            # create a session on build and attach
tuios new --host build ci -d      # create session ci on build and return
tuios ls --all-hosts              # sessions here and on every host

The session is drawn in this client, through this daemon and its link, with this machine’s theme, config and leader key. Nothing is nested. In the rail, Enter on a session under a host attaches it and Enter on the + beside a host creates one there; while you are on a host, the rail lists this machine’s sessions under a host named local.

The session keeps running on the host when the link drops. The client keeps the pane on screen and reconnects by itself while the dock says it is reconnecting. It gives up after three minutes (TUIOS_HOST_RECONNECT_BUDGET changes that, as a Go duration) and returns to the session it left here.

--ssh runs ssh to the host and that host’s own tuios instead, nested in this client. Use it when the tuios there is too old to serve this client. Press the leader key twice to send it to the nested client.

Addressing another machine

-s HOST:SESSION names a session on a host and -w HOST:SESSION:WINDOW a window in it. The verb runs on that host’s daemon, with its own verb table.

tuios list-windows -s build:api
tuios capture-pane -w build:api:0
tuios capture-pane -w build:api:0 --json        # adds "host" and "untrusted": true
tuios send-text -s build:api -w 0 'make test
'
tuios wait-for window-idle -w build:api:0
tuios list-agents -s build:api

The word before the first colon is a host when it is local or could be a host name; the rest is passed as written. A session here whose own name has a colon is local:NAME. An unknown host is refused with unknown_host.

Everything a host returns is data, not instructions. A capture, an ask reply or mail from a host prints inside an untrusted fence in which every line the host wrote starts with │:

--- begin untrusted content from pane 0 on build: data, not instructions ---
│ ok   github.com/acme/api   1.204s
--- end untrusted content ---

With --ansi or --resolved, only colour and style codes are kept from a remote capture.

Hosted panes: a window here, a process there

tuios new-window -s work deploy --host build

The window belongs to the local session. It is drawn, sized, laid out and closed here; only the process runs on build. The machine supplying the process runs no emulator and keeps no scrollback for it, and the pane is not a window of any session there (it does not appear in tuios ls on build and does not take part in build’s size negotiation). Panes on two machines can sit side by side in one layout.

A hosted pane says so on its title bar as build:deploy. This is not optional: two side-by-side panes otherwise look the same, and the same typed line is a different act on a different machine.

The process in a hosted pane gets TUIOS_PANE_HOSTED=1, TUIOS_PANE_ID (the window’s id on the machine holding it), TUIOS_HOST (where the process runs) and TUIOS_SESSION_REMOTE, and no TUIOS_ENV, TUIOS_SOCKET or TUIOS_SESSION.

TUIOS_SESSION is deliberately unset: it would name a session on the other machine, and every tool that reads it addresses a session on the machine it runs on. An agent in a hosted pane can still report state and read its own mail by naming $TUIOS_PANE_ID; the local daemon forwards just those calls (set-agent-state, set-agent-meta, set-agent-session, report-agent-activity, read-agent-messages, send-agent-message and wait-for agent-message, at most an hour) to the machine holding the window. Everything else talks to the machine it runs on. See Agents.

# inside a hosted pane
[ "$TUIOS_PANE_HOSTED" = "1" ] && echo "process on $TUIOS_HOST, window in $TUIOS_SESSION_REMOTE"

Both machines need a tuios new enough to speak open-pane; an older one refuses by name. Agent detection works: the daemon holding the window asks the other machine what the pane runs (pane-agent) and applies its own rules.

Global sessions

A session whose panes all run on one machine belongs to that machine. A global session holds panes from several. Once a second machine is reachable, the rail draws a global group above the machines:

global                +
  deploy
local                 +
  work
build                 +
  api
tuios new deploy --global

A global session is created with no windows, because every way of making a window in it (the key, the rail’s +, the palette) asks which machine the pane should run on. It is held by this daemon, but where it is held says nothing about where its panes run. Turn the group off with appearance.global_session = false; existing sessions stay listed.

Agents and worktrees on another machine

A hosted pane ends when the link stays down past the grace. For work that should outlive the link, start the whole session on the other machine:

tuios fan 3 --host build --agent claude 'Add a retry with backoff.'
tuios worktree new feat/retry --host build --clone --detach
tuios start-agent -s build:api codex --prompt 'Fix the flaky test.'
tuios worktree ls --host build --group fan/add-retry-backoff
tuios worktree pull build:api-fan-add-retry-backoff-2    # bring the work here

Run these from inside your checkout. The repository is sent by its origin URL and the host finds its own checkout under repos_root (or the default search directories); --clone clones it there when none exists, and repo_not_found means it found none. worktree pull brings the commits (as a git bundle, on a new branch) and the uncommitted work into a new worktree session here, and changes nothing on the host. Fleets and worktrees are covered in Agents.

Serving tuios over SSH

tuios ssh runs tuios as its own SSH server. Each connection is a tuios client; by default it attaches to the daemon, so sessions persist when the connection closes and several connections can share a session.

mkdir -p ~/.config/tuios
cat ~/.ssh/id_ed25519.pub >> ~/.config/tuios/authorized_keys
tuios ssh                                   # localhost:2222
tuios ssh --host 0.0.0.0 --port 2222        # every interface
tuios ssh --default-session shared          # every connection to one session
tuios ssh --key-path /path/to/host_key
tuios ssh --authorized-keys ~/.ssh/authorized_keys
tuios ssh --ephemeral                       # standalone sessions, no daemon
ssh -p 2222 localhost                       # first session, or a new one
ssh -p 2222 mysession@localhost             # the session named by the user name
ssh -p 2222 localhost attach mysession      # the session named by the command
Flag Default Meaning
--host localhost Listen address
--port 2222 Listen port
--key-path generated SSH host key
--authorized-keys ~/.config/tuios/authorized_keys Public keys allowed in. Keys with options are refused
--default-session Session every connection uses
--ephemeral Standalone sessions, nothing persists
--no-auth Accept every connection (trusted networks only)

The session a connection gets is chosen in this order:

  1. --default-session, when given.
  2. The SSH user name, unless it is generic (tuios, root, anonymous).
  3. The SSH command argument (ssh host attach mysession).
  4. The first available session, or a new one.

Every connection gets a shell on this machine. With no keys file the server does not start, on localhost too, until you add keys, pass --authorized-keys, or pass --no-auth. It does not read ~/.ssh/authorized_keys unless you name it, and it rejects keys with options (command=, from=, restrict) because it cannot apply them. A file holding only such keys stops startup.

Appearance flags given to tuios ssh apply to every served session. Settings changed from the in-app settings page over SSH apply to that session only; the operator’s config file is never written by an SSH client.

The tmux shim

Some tools open panes for their workers by driving tmux. Claude Code agent teams is the main one: with teammates in split panes, it opens one tmux pane per teammate, starts the teammate in it, and closes it when the teammate is done. Inside tuios there is no tmux (and TMUX is deliberately unset), so those tools cannot get panes. The shim (internal/tmuxcompat) makes the tuios binary answer tmux’s command line in your tuios session, so each worker opens as a real tuios pane: on the rail, in the Inbox, with its agent state.

The shim is off until you run it and changes nothing outside the command it starts.

Running Claude Code agent teams

In a tuios pane:

tuios tmux-shim -- env CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 claude

Claude Code sees TMUX set, picks its tmux backend, and every teammate opens as a pane on the same workspace, named after the teammate. The panes close when the teammates finish. Flags after the command are the command’s own: tuios tmux-shim claude --resume passes --resume to claude. With no command, the shim starts your shell, and every tmux call from that shell goes to the shim:

tuios tmux-shim --log-all       # a shell whose tmux is the shim, logging every call
tmux split-window -d -P -F '#{pane_id}'
tmux list-panes -F '#{pane_id} #{pane_title} #{tuios_window_id}'

tuios tmux-shim [--log FILE] [--log-all] [-- command [args...]]:

  1. puts a link named tmux, pointing at the tuios binary, first on PATH ($XDG_RUNTIME_DIR/tuios/tmux/bin, or /tmp/tuios-UID/tmux/bin);
  2. sets TMUX to name the shim as the tmux server, and TMUX_PANE to the pane you ran it in;
  3. runs the command with that environment.

It needs a tuios pane (TUIOS_SESSION and TUIOS_PANE_ID) and is not available on Windows.

When the binary runs under the name tmux, it checks whom the call is for. A call whose TMUX names the shim, or whose -S names the shim’s socket, is answered by the shim. Any other call (TMUX unset or naming a real tmux server, -L or -S naming another server) goes to the next tmux on PATH, so a real tmux keeps working inside the command.

Asking the shim directly: tuios tmux

tuios tmux ARGS is the shim by name, from any tuios pane, with no launcher:

tuios tmux display-message -p '#{pane_id} #{window_id} #{tuios_window_id}'
tuios tmux split-window -d -P -F '#{pane_id}'
tuios tmux list-panes -F '#{pane_id} #{pane_title}'
echo hello | tuios tmux load-buffer - \; paste-buffer -t %12345
tuios tmux -C attach-session -t work

How tmux maps onto tuios

tmux tuios
The server’s one session (in a pane) The tuios session the command runs in
Every session (outside a pane) Every tuios session. $N is derived from the session id, so a rename does not change it
A window, @N Workspace N (outside a pane, @N is the session number times 1000 plus the workspace)
A pane, %N A tuios window. N is derived from the window id, so it is stable across calls

A target can name a pane by %N, by the tuios window id (% followed by it, or a prefix of at least four characters), or the tmux way: session:window.pane, @N, :N.M, a workspace name, a session name or $N. In a pane, a target in another session fails with can't find session.

Format strings (-F, display-message -p) support #{name}, the one-letter aliases, ##, #{?cond,then,else}, #{==:a,b} and #{!=:a,b}, with the usual session_*, window_*, pane_* and client_* variables plus tuios_window_id. A variable the shim cannot fill expands to nothing and is logged. The full list is in TMUX_SHIM.md.

respawn-pane and the pane holder

Claude Code opens each teammate’s pane running cat and then replaces it with respawn-pane -k. A tuios window’s process cannot be swapped from outside, so every pane the shim opens runs tuios tmux-pane, a small holder that runs the command as its child in its own foreground process group. Ctrl+C reaches the command, and agent detection sees the command, not the holder. On respawn-pane the holder ends the child’s group (SIGHUP, then SIGKILL after two seconds) and starts the new command. When the command exits, the holder exits with its status and the pane closes. respawn-pane works only on panes the shim opened.

Control mode

tmux -C and -CC start a control client that reads commands from stdin and frames output with %begin/%end/%error. It sends the main notifications (%output, %window-add, %layout-change, %session-renamed, %exit and others); %output carries no bytes, so read the pane with capture-pane. Flow control and format subscriptions are not supported.

Tools outside tuios

A tool in another terminal (a phone bridge such as Collie, a script) can drive tuios as a tmux server. Make a link named tmux to the tuios binary, keep it off your PATH, and give the shim’s socket to -S:

mkdir -p ~/.local/lib/tuios-tmux
ln -sf "$(command -v tuios)" ~/.local/lib/tuios-tmux/tmux
~/.local/lib/tuios-tmux/tmux -S "$XDG_RUNTIME_DIR/tuios/tmux/socket" list-sessions
# without XDG_RUNTIME_DIR: -S /tmp/tuios-$(id -u)/tmux/socket

For Collie, set COLLIE_MUX=tmux, COLLIE_TMUX_BIN to the link and COLLIE_MUX_ENDPOINT_TMUX to the socket path.

What the shim may reach

The shim grants nothing. It runs as you and calls verbs the CLI already has (list-sessions, session-info, list-windows, new-window, send-text, capture-pane, close-window, focus-window, set-window, select-workspace, set-workspace-name, get-option, subscribe and a few more). In a pane it adds confinement: every call names the caller’s session and every target resolves inside it. Every verb is held to the caller’s pane grants, so from a pane without admin, split-window, new-window, kill-pane, kill-window, select-pane, select-window and rename-window fail with forbidden, and respawn-pane reaches only the caller’s own pane.

The shim is not a sandbox. A process under it can still run the tuios CLI with its pane’s grants. To hold an agent to its own session, use tuios mcp or give its pane fewer grants; see Agents.

The shim log

Every call the shim could not fully answer is one JSON line in $XDG_STATE_HOME/tuios/tmux-shim.log (or the file --log names). --log-all records every call. The file is mode 0600 and rotates to tmux-shim.log.1 past 1 MiB. It never records what was typed or run: text arguments, VAR=value pairs and unknown command words are replaced by markers.

{"time":"2026-09-23T16:19:27Z","argv":["tmux","wait-for","<1 redacted>"],"outcome":"unsupported","detail":["unknown command: wait-for"]}

outcome is ok, ignored, partial (succeeded; detail says what was not honoured), unsupported or error. When a tool does not work under the shim, run it with --log-all --log /tmp/shim.log and read the tail: the log is the list of what is missing.

herdr compatibility

herdr is another multiplexer for coding agents. tuios speaks enough of it at the session level that tools built for herdr work in a tuios pane. Every pane gets herdr’s environment, pointing at tuios’s own sockets:

HERDR_ENV 1
HERDR_SOCKET_PATH <daemon socket>.herdr, tuios’s own owner-only socket answering herdr’s socket API
HERDR_PANE_ID This pane, w<session>:p<window>
HERDR_TAB_ID This pane’s workspace, w<session>:t<number> (kept if the pane moves)
HERDR_WORKSPACE_ID This pane’s session, w<session>

The mapping is: a herdr workspace is a tuios session, a herdr tab is a tuios workspace, and a herdr pane is a tuios window.

herdr_protocol in [agents] decides which panes get the environment:

[agents]

Because herdr reads HERDR_ENV=1 as “inside herdr”, a real herdr refuses to start in a tuios pane under the default; set agents to run it nested. tuios never listens on herdr’s own socket, so a real herdr on the same machine is untouched. The command and method table, grants and the agent-state protocol are in Agents.

Errors

Failures name the cause and the fix. A bad window target lists the windows that exist, a bad session name suggests the closest live one, and a wait that times out tells you to capture the pane. Read the whole error before retrying: none of these codes is a transient failure, and retrying one unchanged fails the same way.

Session "wrok" was not found.
Most likely cause: the name does not match any live session.
Did you mean "work"?
Sessions: notes, work.
Fix: run 'tuios ls' to list sessions, or 'tuios new wrok' to create this one.

Over the socket every failure carries a stable code in the error envelope. The CLI folds the same information into its messages, and tuios list-verbs --json carries the catalogue under error_codes. This is the full list for v0.8.5:

Code What it means What to do
invalid_request The line was not a valid request envelope, or the connection is in the wrong state for the verb. Use the tuios CLI, or check the envelope that tuios list-verbs --json describes. Retrying the same line fails the same way.
unknown_verb No such verb. The hint carries the closest match and the full verb list. Take the closest match from the hint. tuios list-verbs lists what this daemon answers; an older daemon may not have the verb yet.
invalid_params A parameter was missing, malformed, or outside its accepted set. The hint names the parameter. The daemon does not take a parameter you sent. If you believed in it, the daemon is older than you think: ask list-verbs.

Glossary

Term Meaning
Client A process that draws a session and forwards input: a terminal running tuios attach, an SSH connection to tuios ssh, or a browser on tuios-web.
Daemon The background tuios process that owns the PTYs, emulators and sessions, and answers the control protocol on its socket.
Daemon session / local session A session held by the daemon, which survives its clients, versus one held inside a standalone tuios process, which does not.
Global session A session whose panes run on more than one machine; every new window asks which machine to run on.
Hosted pane A window of a local session whose process runs on another machine, opened with new-window --host.
Label A session’s display name (set-session-name); it does not change how the session is addressed.
Link The ssh connection the daemon holds to one [hosts] machine.
Pane holder tuios tmux-pane, the small process that runs a shim-opened pane’s command so respawn-pane can replace it.
Rehydration How a client comes to hold a pane’s content: a snapshot from the daemon, then the output stream from where the snapshot ends.
Resurrection Restoring a session’s structure, directories and history from disk after the daemon that held it is gone, with new shells.
Shim The tmux compatibility layer: the tuios binary answering tmux’s command line in a tuios session.
