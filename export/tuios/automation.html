Chapter 8 tuios manual

TUIOS: Tape Scripting, Recording, Screenshots and Scripted Workflows

How to drive tuios without touching the keyboard, with tape scripts, recorded tapes, project tapes, screenshots and shell scripts built on the control commands.

tuiosautomationtapescriptingscreenshots

tuios can be driven by something other than your hands. A tape is a small script of keystrokes and window-manager commands that tuios plays back in a visible session. You can write one, record one, or keep one in a project directory so that entering the directory builds your layout. Separately, every part of a running session is reachable from a shell through commands such as tuios new-window, tuios send-text, tuios run and tuios wait-for, which is how you build scripts, CI helpers and hooks. This chapter covers all of it, including screenshots, and ends with six complete scripts you can adapt.

Choosing a mechanism

There are five ways to automate tuios. They overlap, but each has one job it does best.

Mechanism Entry point Runs where Best for
Tape playback tuios tape play FILE A fresh, visible, standalone tuios started for the tape Demos, reproducible walkthroughs, bug reproductions
Tape execution tuios tape exec FILE The attached client of a running daemon session Replaying a short tape into the session you are already using
Tape recording Ctrl+b T r In the TUI Capturing what you just did, then editing it into a script
Project tapes .tuios.tape in a directory The focused shell’s session, after you review it A per-project layout built when you cd into the project
Control commands tuios new-window, send-text, run, wait-for, … The daemon, attached or detached Shell scripts, CI, hooks, agents

If you are writing a script that must work reliably, prefer the control commands over tapes. They address windows by name or id, they work on a detached session, they report what changed, and tuios wait-for blocks on real events instead of guessing with Sleep. Tapes drive whichever window has the focus, which is right for a demo and fragile for a build.

Tape scripting

What a tape is

A tape is a plain text file, conventionally with the .tape extension, that holds one command per line. Each command either sends input to the focused window’s terminal (Type, Enter, Ctrl+C), or performs a window-manager action (NewWindow, EnableTiling, SwitchWorkspace 2), or controls playback timing (Sleep, WaitUntilRegex). The language looks like the tape format of Charm’s VHS, and borrows its spelling, but it is tuios’s own language with its own parser (see VHS and tuios tapes).

# hello.tape
DisableAnimations
NewWindow
Sleep 500ms
Type "echo Hello from TUIOS"
Enter
Sleep 1s
EnableAnimations

The upstream reference for the language lives at https://tuios.dev/docs/tape-scripting; the repository’s TAPE_SCRIPTING.md points there. Everything below is checked against the v0.8.5 parser (internal/tape/lexer.go, parser.go) and executor (executor.go), and the example outputs come from running tuios tape validate on v0.8.5.

The tape subcommands

There is one top-level command, tuios tape, with seven subcommands. There is no tuios --tape flag and no tape record or tape run subcommand: recording happens inside the TUI.

Command What it does
tuios tape play <file.tape> Start a new, visible tuios and play the tape in it
tuios tape exec <file.tape> [-s SESSION] Send the tape to a running daemon session and play it through that session’s attached client
tuios tape validate <file.tape> Parse the file, print every error, or print a numbered command summary
tuios tape list List the tapes in the recordings directory, newest first, with size and date
tuios tape show <name> Print a saved tape (by name, with or without .tape)
tuios tape delete <name> Delete a saved tape after a yes/no prompt
tuios tape dir Print the recordings directory 
tuios tape validate examples/demo.tape
tuios tape play examples/demo.tape
tuios tape exec --session work examples/simple.tape
tuios tape dir

tape play

tuios tape play reads and parses the whole file first. If there is any parse error it prints the errors and exits without starting the TUI:

Tape parsing errors:
  line 3: Sleep command expects a duration, got NUMBER

Otherwise it prints the command count and starts a tuios of its own.

The playback tuios is a fresh, standalone one (a local client, not the daemon), so it touches none of your sessions, and it starts with no windows: that is why almost every tape begins with NewWindow. It loads your config.toml, accepts the appearance flags of tuios (--theme, --border-style, --show-keys, --no-animations and the rest), and forces animations off at start. Before each command it waits for running animations and for any window the previous command asked for (up to 5 seconds), so a Type after NewWindow lands in the new window. A failing command shows a Script error: ... notification and playback goes on. When the tape ends, tuios shows a completion indicator and stays open; quit it as usual.

--show-keys is useful for recording a demo of a tape: the showkeys overlay displays the keys the tape presses. tuios tape play --show-keys --theme dracula demo.tape

During playback Ctrl+p pauses and resumes. It is the script_pause action in [keybindings.script], and it is live only while a tape plays, which is why it can share Ctrl+p with the command palette.

[keybindings.script]
script_pause = ["ctrl+p"]

tape exec

tuios tape exec sends the file’s text to the daemon, which forwards it to the TUI client attached to the target session. The tape then runs inside that session, against its windows and focus.

tuios tape exec demo.tape                 # most recently active session
tuios tape exec --session mysession demo.tape

It differs from tape play in several ways:

Behaviour tape play tape exec
Needs a daemon No Yes
Needs an attached client It is the client Yes: a headless session answers tape scripts need an attached client. A headless daemon has no renderer to run them
Parse errors Reported, nothing runs Unparseable lines are skipped; it refuses only a file with no commands at all (tape script has no commands or contains errors)
Sleep Honoured Honoured
Wait Honoured, same as Sleep Skipped (no delay)
WaitUntilRegex Blocks until match or timeout Skipped
Gap between commands Paced by the render loop 50 ms after each command

Because tape exec skips Wait and WaitUntilRegex, a tape that relies on them for correctness runs too fast under exec. Use Sleep for delays you need under both, or validate the tape with tape play and drive the live session with control commands instead.

From inside a tuios pane, tape exec is held to the pane’s grants. A pane without the respond grant may not run a tape that types or presses keys (Type, Enter, the key commands, key combinations, Source and LoadLayout), because the client types into whatever pane has the focus. The refusal names the reason and suggests send-keys or send-text with a window. See Agents for grants.

tape validate

validate parses the file and nothing more. On success it prints the count and a numbered summary of how each line was understood, which is the fastest way to see what the parser kept and what it dropped:

Parsing errors found:
  ✗ line 1: unexpected token: IDENTIFIER

tape file has parsing errors

Lexical rules

The rules below are what the v0.8.5 lexer and parser do.

Rule Detail
One command per line A newline ends a command. Anything left on the line after the command’s arguments is silently ignored, so Type "ls" Enter types ls and drops the Enter.
Comments # starts a comment that runs to the end of the line, anywhere outside a string. Blank lines are ignored.
Keywords Case-insensitive: Type, type and TYPE are the same command.
Strings Double quotes "...", single quotes '...' or backticks `...`.
Escapes in strings \n \t \r \\ \" \' \` \a \b \f \v, plus \xHH (one byte), \uHHHH and \UHHHHHHHH (one Unicode code point). An unknown escape keeps the letter: \q is q.
Durations A number with a Go duration unit: 500ms, 2s, 1.5s, 1m, 1m30s, 1h. A bare number is not a duration: Sleep 500 is an error.
Numbers Digits with an optional decimal part: 3, 2000.
Delay modifier @<duration> right after the keyword: Type@100ms "x", Enter@200ms. See the note below.
Repeat count A number after a key command repeats it: Down 5, Backspace 10.
Identifiers Letters, digits and _. A . or - ends an identifier, so quote file and layout names that contain them.

The @ delay modifier parses but has no effect in v0.8.5. The parser stores it, but playback uses a command’s delay only for Sleep and Wait. A Type@1s "hello" line sends hello in one write, immediately. Use an explicit Sleep between commands to pace a demo.

The sections below give each command’s arguments, behaviour and an example.

Typing and keys

Type

Type "text"

Type writes the string to the focused window’s terminal, byte for byte, in one write. It needs a string; Type hello (no quotes) is the error Type command expects a string, got IDENTIFIER. It does not press Enter.

Type "git status"
Enter
Type "printf 'a\\tb\\n'"   # \\ in the tape is one backslash for the shell
Enter

Type and the key commands write straight to the focused window’s terminal, whatever mode tuios is in, so a tape does not need TerminalMode for its text to arrive. The shipped examples still bracket typing with TerminalMode and WindowManagementMode, which keeps the on-screen mode indicator honest and leaves tuios in the right mode for a person who takes over after the tape. The mode does matter when real keys are pressed: under VHS, or with tuios send-keys without -w, text typed in window-management mode is read as tuios keybindings (t toggles tiling, and so on).

Enter, Space, Backspace, Delete, Tab, Escape and the cursor keys

Each sends the fixed byte sequence listed in the quick reference to the focused window, once, or N times with a trailing count.

Type "hello wrold"
Backspace 5
Type "world"
Enter
Up 2          # recall the command from two lines back
Escape

The cursor keys are always sent in normal mode (ESC [ A). A program that switched on application cursor keys (vim, less) accepts these anyway in most cases. tuios send-keys is smarter here: it sends the form the program asked for.

Key combinations

Ctrl+<key>   Alt+<key>   Shift+<key>   Ctrl+Alt+<key>   Opt+<key>

A key combination is one or more modifiers joined to a final key with +. The final key may be a letter, a digit, an identifier such as space or enter, or Enter, Space and the cursor-key keywords. Modifiers are case-insensitive, and Opt is a synonym for Alt.

The combination is converted to bytes and written to the focused window:

Combination Bytes
Ctrl+<letter> The control character: Ctrl+c is 0x03, Ctrl+b is 0x02
Ctrl+<digit> The digit AND 0x1f
Alt+<char> ESC then the character
Shift+<char> The upper-case character
Alt+space, Alt+enter, … ESC then the named key’s byte
Ctrl+space, Ctrl+enter, … The named key’s byte (the Ctrl is dropped)
Ctrl+Up, Alt+Home, … The key’s name as text (Up), since only the names space, enter, return, tab, escape, esc, backspace and delete are mapped. Avoid these
Alt+1 … Alt+9 Not sent: switches to that workspace 
Type "sleep 100"
Enter
Sleep 1s
Ctrl+c          # interrupt it
Ctrl+l          # clear the screen
Alt+2           # go to workspace 2

A key combination is sent to the program in the focused window, never to tuios: Ctrl+b is the byte 0x02 for the shell, not the tuios leader, so a tape cannot open a prefix menu. Use the tape commands for tuios actions, or tuios send-keys "PREFIX n" (no -w) from a shell. And Shift+Tab does not parse in v0.8.5 (expected key after modifier, got Tab); send a back-tab with tuios send-keys -w NAME BTab.

Timing and waiting

Sleep and Wait

Sleep <duration>
Wait <duration>

Both pause playback for the duration. Wait is an alias kept for compatibility, with one difference: tape exec skips it. A bare number is an error (Sleep command expects a duration, got NUMBER).

Sleep 300ms
Sleep 2s
Sleep 1m30s
Wait 500ms

WaitUntilRegex

WaitUntilRegex "pattern" [timeout_ms]

WaitUntilRegex blocks playback until the visible screen of the focused window matches a Go regular expression (RE2 syntax), or until the timeout passes. The timeout is an optional integer number of milliseconds; it defaults to 5000. A timeout is not fatal: tuios shows a WaitUntilRegex: timed out warning and continues with the next command. An invalid pattern shows WaitUntilRegex: invalid pattern: ... and the command is skipped without waiting.

Type "make build"
Enter
WaitUntilRegex "Build (succeeded|failed)" 120000

The pattern must be a quoted string (WaitUntilRegex /ready/ is a parse error). It is matched against the window’s visible screen, not its scrollback, so a line that scrolled off no longer matches. String escapes are processed first: write "\\$" for the regex \$ and "\\d+" for \d+. tape exec skips the command.

Because the typed command is itself on screen, waiting for a word it contains matches immediately. Wait for something only the output can contain, such as "^ok " or "[0-9]+ passed". The same trap exists for tuios wait-for; the marker section shows the general fix.

Modes

TerminalMode
WindowManagementMode

TerminalMode switches to terminal mode (and focuses the first non-minimized window if none is focused); WindowManagementMode switches to window-management mode. See Concepts for the modes, and the note under Type for why tapes bracket typing with them.

Windows

NewWindow waits (up to 5 s) for the window to exist before the next command runs. FocusWindow tries a window name first, then a full window id; an id that matches nothing does nothing, silently. RenameWindow takes a quoted string or a bare word. CloseWindow, MinimizeWindow and RestoreWindow act on the focused window.

NewWindow
RenameWindow "server"
TerminalMode
Type "python3 -m http.server 8000"
Enter
WindowManagementMode
NewWindow
RenameWindow "client"
FocusWindow server

In a tape file these commands take only the arguments shown. NewWindow "name" and CloseWindow "name" parse, but the name is discarded. The forms with a name (NewWindow [name], CloseWindow [name], MinimizeWindow [name], RestoreWindow [name], RenameWindow <old> <new>) exist only through tuios run-command. FocusWindow takes a bare word, so a name with spaces or dots cannot be focused from a tape; use a simple name.

Tiling and layout

SmartSplit splits the focused pane along its longer side and fails with tiling off. SnapLeft, SnapRight and SnapFullscreen act on a floating window. SaveLayout NAME saves a layout template and LoadLayout NAME applies one; an unknown name shows layout template not found: NAME.

EnableTiling
NewWindow
NewWindow
SmartSplit
EqualizeSplits
SaveLayout dev
DisableTiling
LoadLayout "dev"

Split does not work in a tape file in v0.8.5. The executor needs a direction (horizontal/h or vertical/v), but the tape parser keeps only a number after Split, so Split vertical reaches the executor with no argument and fails with Script error: Split needs horizontal or vertical. Use SmartSplit or NewWindow with tiling on inside a tape, and tuios run-command Split vertical or tuios split-window vertical from a shell. (The project-tape body language, which has its own parser, does accept Split vertical; see Project tapes.)

Workspaces

SwitchWorkspace N
MoveToWorkspace N
MoveAndFollowWorkspace N

Each takes a workspace number. A missing or non-numeric argument is a parse error (SwitchWorkspace expects a number, got IDENTIFIER). MoveToWorkspace moves the focused window and stays; MoveAndFollowWorkspace moves it and switches to that workspace. Alt+N for N in 1 to 9 is a shorthand for SwitchWorkspace N.

SwitchWorkspace 2
NewWindow
MoveAndFollowWorkspace 1

Interface commands

Recorded tapes start with DisableAnimations and end with EnableAnimations. CommandPalette opens the palette for a demo that shows it. Screenshot renders the focused window under screenshot.directory with the [screenshot] options, and the file exists before the next command runs, so a later command can use it.

NewWindow
TerminalMode
Type "ls --color=always"
Enter
Sleep 500ms
Screenshot

Commands that parse and do nothing

Some VHS keywords are accepted so that a VHS-flavoured file still parses, but the v0.8.5 executor has no action for them. They are silently ignored at playback.

Command Parses as Effect
Set <key> <value> Set Theme dracula None. Use tuios --theme or run-command SetTheme
Output <file> Output demo.gif (the identifier stops at the ., so it keeps demo) None. tuios does not render video
Source <file> Source "other.tape" None. A tape cannot include another tape
Focus <name> Focus editor None. A quoted name is a parse error. Use FocusWindow

Because these lines are accepted, tuios tape validate reports them as valid. Do not read a passing validation as proof that every line will do something.

Commands that only run-command reaches

The executor knows more commands than the tape parser does. These have no tape keyword in v0.8.5 and run only through tuios run-command (or the run-command verb):

Split horizontal|vertical, ArrangePanes tiled|even-horizontal|even-vertical [workspace [window...]], SetMultifocus [window...], SetMasterPosition left|right|top|bottom|center, SetMasterCount 1-9, CycleMasterPosition, AddMaster, RemoveMaster, SwapWithMaster, FocusMaster, SetTheme NAME, SetDockbarPosition bottom|top|hidden, SetBorderStyle STYLE, ShowNotification MESSAGE [TYPE], and the read-only ListWindows, GetWindow [id-or-name] and GetSessionInfo (best with --json). The name-taking forms of the window commands (NewWindow [name], CloseWindow [name], RenameWindow <old> <new>) are run-command only too.

tuios run-command Split vertical
tuios run-command ArrangePanes even-horizontal
tuios run-command ShowNotification "Deploy finished" success
tuios run-command --list

run-command also accepts the keymap’s spelling of a name: toggle_tiling, toggletiling and ToggleTiling resolve to the same command. A name that is none of these is an error rather than a silent no-op.

simple.tape

# Simple TUIOS Tape Script            (comment lines trimmed)
DisableAnimations
NewWindow
Sleep 500ms
Type "echo Hello from TUIOS"
Enter
Sleep 1s

Line by line:

  1. DisableAnimations: playback already starts with animations off, so this is belt and braces; it also makes the tape behave the same under tape exec in a session that has animations on.
  2. NewWindow: a tape play session starts empty, so the tape opens a window. Playback holds the next command until the window exists.
  3. Sleep 500ms: gives the new shell time to print its prompt.
  4. Type "echo Hello from TUIOS": writes the text to the focused window, which is the new one. No TerminalMode is needed, because tape typing goes straight to the window’s terminal.
  5. Enter: runs it.
  6. Sleep 1s: leaves the output on screen.
  7. EnableAnimations: restores animations for whatever you do next in that tuios.

# TUIOS Demo with WaitUntilRegex      (comment lines trimmed)
DisableAnimations

  1. A window opens, the tape enters terminal mode and runs an echo.

  1. EnableTiling tiles the session.
  2. NewWindow and Sleep 1s open a shell and let it start.

VHS and tuios tapes

tuios tapes share their look with the .tape files of VHS, Charm’s terminal recorder: Type, Sleep, Enter, Ctrl+C, Backspace 5, Set and Output mean the same kind of thing. They are still two different programs:

The VHS-only keywords Output, Set and Source parse in tuios and do nothing; Require, Hide and Show are parse errors; and VHS has none of the window-manager commands. VHS renders a terminal to GIF, MP4 or WebM; a tuios tape drives a live tuios.

To make a video of tuios, run tuios under VHS. The tuios repository does this for its README recording (assets/demo.tape, rendered by assets/record-demo.sh), with a VHS tape whose Type lines start tuios and press its keys. Inside such a recording you can also call tuios tape play to let a tuios tape do the window choreography while VHS records the frames.

The upstream recording notes one limit worth knowing: VHS has no Alt+Space or Alt+Escape, so the tuios bindings on those keys cannot be pressed from a VHS tape. The README demo opens the launcher from the command palette instead.

Tape recording

Recording turns what you do in the TUI into a tape you can replay and edit. It is in-app only; the upstream guide is https://tuios.dev/docs/tape-recording.

Keys

All recording keys live under the tape prefix, Ctrl+b T (capital T), in [keybindings.tape_prefix]:

Keys Action What it does
Ctrl+b T r tape_prefix_record Open the naming prompt, then start recording
Ctrl+b T s tape_prefix_stop Stop and save the recording
Ctrl+b T m tape_prefix_manager Open the tape manager
Ctrl+b T t tape_prefix_review Review the project tape (see Project tapes)
Ctrl+b T Esc tape_prefix_cancel Leave the prefix

Example: record a short session

Press Ctrl+b T r. A prompt offers a name such as recording_20261007_142530; edit it to git-tour and press Enter. A Recording started: git-tour notification appears and, if a window is focused, tuios enters terminal mode. Type git log --oneline -5, press Enter, switch to workspace 2 and back, then press Ctrl+b T s: Recording saved: git-tour.tape. tuios tape show git-tour prints it.

Pressing record while already recording shows Already recording; stop while not recording shows Not recording. Esc in the naming prompt goes back to the manager’s list without recording.

What is recorded

The recorder captures three kinds of event, and it writes the time between events as Sleep lines.

You do Recorded as
Type printable characters in terminal mode Accumulated into one Type "..." per run of characters
Press Enter, Space, Backspace, Delete, Tab, Esc, arrows, Home, End Enter, Space, Backspace, Delete, Tab, Escape, Up…
Press another key with Ctrl, Alt or Shift A key combination line, such as ctrl+c
Switch mode TerminalMode or WindowManagementMode
Switch workspace SwitchWorkspace N
New, close, next, previous, minimize, restore-all window actions NewWindow, CloseWindow, NextWindow, PrevWindow, MinimizeWindow, RestoreWindow
Toggle tiling, snap left, right or fullscreen ToggleTiling, SnapLeft, SnapRight, SnapFullscreen
Select window N FocusWindow N

At the start the recorder writes the state you were in, so replay starts from the same place: SwitchWorkspace N when you were not on workspace 1, then EnableTiling or DisableTiling, then TerminalMode or WindowManagementMode.

Project tapes

A project tape is a file named .tuios.tape in a project directory. When the focused shell inside tuios enters a directory that holds one, tuios can build a session and layout for the project from it, the way a .envrc works for direnv. The full upstream description is PROJECT_TAPES.md.

A tape is arbitrary command execution (Type "curl x | sh" Enter is a legal tape), so the feature is built around one rule: an untrusted tape is inert. tuios only stats it, reads it once, hashes it and shows it to you. Nothing runs until you have read it and chosen to run or trust it.

Quick start

# ~/src/myproject/.tuios.tape
Session "myproject"
Require "pnpm"

RenameWindow "edit"
Type "nvim ." Enter

Split vertical
RenameWindow "serve"
Run "pnpm dev"

Split horizontal
RenameWindow "sh"

Focus "edit"
  1. In a tuios pane, cd ~/src/myproject. About 400 ms later a passive banner slides in and a tape ? badge appears in the dock. Nothing has run, and your shell did not lose a keystroke.
  2. Press Ctrl+b T t, or choose Tape: review the project tape in the command palette. The review dialog shows the canonical path, the trust status (including “changed since you trusted it”), a one-line summary such as session "myproject" from a header parse that executes nothing, and the full content, scrollable with Up and Down. You approve what you can see.
  3. Choose: r Run once (remember nothing), t Trust and run (remember this exact file), n Never (never prompt for this path), or Esc Not now (the badge stays).
  4. On later visits the badge reads tape ✓, and one keypress runs it, which, once the session exists, just switches you to it.

The dialog opens only when you ask for it, or on detection with auto_review = true. It never steals focus because you typed cd.

The trust model

Trust is granted per pair of canonical path and content hash, as direnv does. The path is the realpath of the tape and the hash is the SHA-256 of its bytes, so any edit reverts the tape to untrusted: a git pull that changes a trusted tape shows up as a “changed since you trusted it” prompt, never as a silent run. tuios reads the file once, and hashes, shows and runs that same buffer, so swapping the file or a symlink target after you approve changes nothing. Decisions live in $XDG_DATA_HOME/tuios/tape-trust.toml (mode 0600), which is per-machine state; do not sync it with your dotfiles.

Status Cause What you see
Untrusted Never decided, or edited since trusted Banner, badge, dialog on request
Trusted Trust and run on these exact bytes tape ✓; runs on a keypress, or on entry in auto
Denied Never, keyed by path only, so edits do not re-prompt Nothing at all
Ineligible Fails a hygiene check A passive notice; the dialog offers only Dismiss, with no override

A tape is eligible only if it is a regular file after symlink resolution, owned by you, not group- or world-writable, has no world-writable directory without the sticky bit on its path, and is at most 64 KiB, the way sshd checks authorized_keys.

What running a project tape does

Scope session (the default) is the tmux-sessionizer model. tuios derives the session name (Session, else the basename). If that session already exists, it switches to it and rebuilds nothing: the session is the durable artifact and the tape is its constructor, run once. Otherwise it creates the session, seeds one window whose shell starts at the project root, runs the body and switches you there. Session scope needs a daemon-backed session; outside one, tuios runs the tape in the current session and says so.

Scope current applies the body to the current session from the focused window, composing with whatever exists. Keep such tapes tiny:

# .tuios.tape: one split running the watcher
Scope current
Split horizontal
Run "make watch"

Two more guarantees: detection is off while a tape runs, and a project root handled in this run does not re-trigger, so a tape that cds onward cannot chain another tape. Remote (SSH) shells are ignored, since tuios cannot read or verify a file on another machine.

Markers and the one trap in window-output

window-output matches the whole scrollback, including text that was there before the wait started. The pane echoes the command you typed, so a marker written literally in the command matches its own echo at once, and a fixed marker from an earlier run matches again next time. Make the marker fresh, and let the shell assemble it so the echo cannot match:

n=$(date +%s)
tuios send-text -s work -w build "go test ./... ; printf 'tests_done_%s_rc=%s\n' $n \$?
"
tuios wait-for window-output -s work -w build --pattern "tests_done_${n}_rc=[0-9]+" --timeout 300000
rc=$(tuios capture-pane -s work -w build --scrollback --lines 200 |
     grep -o "tests_done_${n}_rc=[0-9]*" | tail -1 | cut -d= -f2)
echo "exit status: $rc"

The echoed line reads printf 'tests_done_%s_rc=%s\n' 1791367393 $?, which the pattern does not match; the output reads tests_done_1791367393_rc=0, which it does. This is the fallback for panes without shell integration. With it, prefer tuios run, or wait-for command-finished, which reports the exit code directly.

A third pattern needs neither: run the work in a window that exits, and wait for the exit.

tuios new-window -s work job
tuios send-text -s work -w job 'go test ./... > /tmp/test.log 2>&1; exit
'
tuios wait-for window-exit -s work -w job --timeout 300000
tail -60 /tmp/test.log

printf 'a\nb\nc\n' | tuios xpanes -c 'echo {}; exec $SHELL'
ls /var/log/*.log | tuios xpanes -l even-horizontal --no-sync -c 'tail -f {}'
tuios xpanes -n 2 -c 'diff {}' a.txt b.txt c.txt d.txt
tuios xpanes -ss --interval 1 -c 'curl -s https://{}/health' web1 web2 web3
tuios close-workspace 2      # close them all again

Popups

popup runs one command in a floating pane centred over the layout. The pane closes when the command exits; it is not tiled, not in the window cycle, and cannot be minimized. It needs an attached client.

Flag Meaning
--width, --height Cells or percent of the pane region (defaults 80% and 60%)
--wait Stay until the command exits, and exit with its status
--capture-stdout Print the command’s stdout here instead of in the popup (implies --wait; not on Windows)
--timeout MS With --wait
--name, --cwd, --workspace, -s Placement
--json Print the popup’s id 
file=$(tuios popup --capture-stdout -- fzf)
tuios popup --wait -- gum confirm "Deploy?" && ./deploy.sh
tuios popup --width 60 --height 20 -- gum choose one two three
tuios popup --width 90% --height 80% -- htop

A popup closed by hand exits 130.

Error codes a script should know

Over the socket every failure carries a stable code; the CLI folds it into its message. The ones scripts meet most:

Code Meaning What to do
session_not_found, window_not_found Bad target; the error lists what exists Fix the name, or create it first
session_exists new with a name already taken Attach to it, or pick another name
needs_client A geometry command on a detached session Attach, or use a verb that needs none
timeout wait-for or run gave up Capture the pane; for run, continue with wait-for command-finished --command-seq N
no_shell_integration, not_at_prompt From run; nothing typed Use send-text and a marker
forbidden The calling pane lacks a grant See tuios pane-grants

tuios ls signals the daemon’s state by exit code: 0 for a running daemon (even with no sessions), 3 for no daemon (saved sessions are listed with "saved": true), 1 for a failure.

Worked scripts

Six complete scripts. Each is bash, uses only commands from this chapter, and takes the session name as its first argument so you can run several at once.

1. Open a dev layout: editor, server, logs

Creates the session if it is missing, opens three named windows in the project directory, starts each program, and attaches. Running it again just attaches.

#!/usr/bin/env bash
# dev-layout.sh SESSION [DIR]
set -euo pipefail
S=${1:-dev}
DIR=$(cd "${2:-$PWD}" && pwd)

exists() {
  tuios ls --json 2>/dev/null | jq -e --arg s "$S" 'any(.[]; .name == $s)' >/dev/null
}

if ! exists; then
  tuios new "$S" --detach
  tuios wait-for session-exists -s "$S" --timeout 10000

  # The detached session starts with one window: make it the editor.
  tuios set-window -s "$S" --name editor
  tuios send-text -s "$S" -w editor "cd $(printf '%q' "$DIR") && \${EDITOR:-vi} .
"
  tuios new-window -s "$S" server --cwd "$DIR" --no-focus
  tuios new-window -s "$S" logs   --cwd "$DIR" --no-focus

  # Let each shell draw its prompt before typing into it.
  tuios wait-for window-idle -s "$S" -w server --idle 300 --timeout 10000
  tuios send-text -s "$S" -w server 'npm run dev
'
  tuios wait-for window-idle -s "$S" -w logs --idle 300 --timeout 10000
  tuios send-text -s "$S" -w logs 'tail -n 50 -F log/development.log
'
  tuios focus-window -s "$S" editor
fi

exec tuios attach "$S"

The windows are opened on a detached session, so they get a nominal size; the layout is computed when the client attaches. With startup.tiled = true (the default for a new install) they come up tiled. To split instead of tile, run tuios split-window after attach from another shell, since splits need an attached client.

2. Run the test suite in a pane and wait for a marker

Uses tuios run when the pane’s shell has OSC 133 integration, and falls back to a fresh marker otherwise. Either way the script’s exit status is the suite’s.

#!/usr/bin/env bash
# test-in-pane.sh SESSION [WINDOW] [COMMAND...]
set -uo pipefail
S=${1:?session}; W=${2:-tests}; shift 2 || true
CMD=${*:-go test ./...}

# Make sure the pane exists.
if ! tuios list-windows -s "$S" --json |
     jq -e --arg w "$W" 'any(.windows[]; .display_name == $w)' >/dev/null; then
  tuios new-window -s "$S" "$W" --cwd "$PWD" --no-focus >/dev/null
  tuios wait-for window-idle -s "$S" -w "$W" --idle 500 --timeout 10000
fi

marks=$(tuios list-windows -s "$S" --json |
        jq -r --arg w "$W" '.windows[] | select(.display_name == $w) | .marks_commands // false')

if [ "$marks" = true ]; then
  tuios run -s "$S" -w "$W" --timeout 1800000 --lines 80 -- "$CMD"
  exit $?
fi

n=$(date +%s)$$
tuios send-text -s "$S" -w "$W" "$CMD ; printf 'tdone_%s_rc=%s\n' $n \$?
"
if ! tuios wait-for window-output -s "$S" -w "$W" \
       --pattern "tdone_${n}_rc=[0-9]+" --timeout 1800000; then
  echo "timed out; last lines:" >&2
  tuios capture-pane -s "$S" -w "$W" --scrollback --lines 40 >&2
  exit 124
fi
out=$(tuios capture-pane -s "$S" -w "$W" --scrollback --lines 400)
rc=$(printf '%s\n' "$out" | grep -o "tdone_${n}_rc=[0-9]*" | tail -1 | cut -d= -f2)
printf '%s\n' "$out" | tail -80
exit "${rc:-1}"
./test-in-pane.sh work tests make test
echo "suite exited $?"

3. Fan work over xpanes

Runs one command per item in its own pane, waits for every pane’s marker, reports each result, and closes the workspace.

#!/usr/bin/env bash
# fan-xpanes.sh SESSION ITEM...
# Example: fan-xpanes.sh work ./api ./web ./worker
set -euo pipefail
S=${1:?session}; shift
[ $# -gt 0 ] || { echo "usage: $0 SESSION ITEM..." >&2; exit 2; }

ids=$(tuios xpanes --session "$S" --no-sync --json \
        -c 'cd {} && make test; printf "xp_done_%s_rc=%s\n" "$TUIOS_XPANES_INDEX" $?' \
        "$@" | jq -r '.. | .window_id? // empty')

fail=0; i=0
for id in $ids; do
  i=$((i + 1))
  tuios wait-for window-output -s "$S" -w "$id" \
    --pattern "xp_done_${i}_rc=[0-9]+" --timeout 1800000
  rc=$(tuios capture-pane -s "$S" -w "$id" --scrollback --lines 200 |
       grep -o "xp_done_${i}_rc=[0-9]*" | tail -1 | cut -d= -f2)
  name=$(tuios get-window -s "$S" "$id" --json | jq -r '.display_name // .title')
  printf '%-20s rc=%s\n' "$name" "$rc"
  [ "$rc" = 0 ] || fail=1
done

ws=$(tuios get-window -s "$S" "$(printf '%s\n' $ids | head -1)" --json | jq -r '.workspace')
[ "$fail" = 0 ] && tuios close-workspace -s "$S" "$ws"
exit "$fail"

The marker is printed with "$TUIOS_XPANES_INDEX", a variable the echo shows unexpanded, so the echo never matches. The script leaves the workspace open when anything failed so you can read the panes. The jq expression collects every window_id in the JSON, whatever its nesting; run tuios xpanes --json ... once and look at it if you want a tighter filter. The display_name and workspace keys come from get-window --json.

4. Watch a log for a regex, then notify

Tails a log in a dedicated window and blocks until a line matches. Then it raises a tuios notification, a desktop notification, and a screenshot of the window for the record.

#!/usr/bin/env bash
# watch-log.sh SESSION LOGFILE [REGEX]
set -euo pipefail
S=${1:?session}; LOG=${2:?logfile}; RE=${3:-'ERROR|FATAL|panic:'}
W=watch-$(basename "$LOG")

# -n 0: start at the end, so old lines already in the file cannot match.
id=$(tuios new-window -s "$S" "$W" --no-focus --print-id -- tail -n 0 -F "$LOG")

if tuios wait-for window-output -s "$S" -w "$id" --pattern "$RE" --timeout 86400000; then
  line=$(tuios capture-pane -s "$S" -w "$id" --scrollback | grep -E "$RE" | tail -1)
  shot=$(tuios screenshot -s "$S" -w "$id" --no-copy --format png)
  tuios run-command -s "$S" ShowNotification "$W: ${line:0:80}" error ||
    true                                   # needs an attached client
  if command -v notify-send >/dev/null; then
    notify-send "tuios: $W" "$line"
  elif command -v osascript >/dev/null; then
    osascript -e "display notification \"${line//\"/}\" with title \"tuios: $W\""
  fi
  echo "matched: $line"
  echo "screenshot: $shot"
fi
tuios run-command -s "$S" CloseWindow "$id" || true

window-output keeps matching once the text is in the scrollback, so do not loop on the same window: the second wait returns at once. To watch again, close the window and open a new one (run the script in a loop), or follow the stream in your own process instead (tail -n 0 -F "$LOG" | grep -m1 -E "$RE").

5. A startup script with [startup]

The [startup] table decides how a new session starts. It has no option that runs commands: there is no startup script hook in v0.8.5. You combine it with a script (or with a project tape) to get a scripted start.

Option Type Default Meaning
startup.open_default_window bool false Open one terminal when a session starts empty
startup.tiled bool true Start a new session tiled instead of floating
startup.start_in_terminal_mode bool false Start focused in terminal mode when a window is present
startup.layout string bsp Tiling scheme a new session starts in; an existing session keeps its own
startup.daemon bool true Make a bare tuios attach to a daemon-backed session; TUIOS_NO_DAEMON=1 or --standalone overrides it

The booleans have no fill-in for a missing key. A config file that predates them and does not name them reads them as false, so an existing install keeps its floating, standalone start; the true defaults reach a new install only. Name them explicitly if you rely on them.

# ~/.config/tuios/config.toml
[startup]
daemon = true
tiled = true
layout = "master-stack"
start_in_terminal_mode = true
open_default_window = false

[appearance]
master_position = "left"
master_ratio = 60

Run the script below instead of tuios. It builds the main session once per daemon start, then attaches. If you call it from a shell rc file, guard it with [ -z "$TUIOS_SESSION" ], which tuios sets in its panes, so a pane’s shell does not try to attach to tuios from inside tuios.

#!/usr/bin/env bash
# tuios-up: build the main session once, then attach
set -euo pipefail
S=main

tuios ls >/dev/null 2>&1 || true        # exit 3 just means no daemon yet

if ! tuios ls --json 2>/dev/null | jq -e --arg s "$S" 'any(.[]; .name == $s)' >/dev/null; then
  tuios new "$S" --detach
  tuios wait-for session-exists -s "$S" --timeout 10000
  tuios set-window -s "$S" --name shell
  tuios new-window -s "$S" notes  --cwd ~/notes --no-focus -- "${EDITOR:-vi}" .
  tuios new-window -s "$S" top    --no-focus -- htop
  tuios new-window -s "$S" mail   --workspace 2 --no-focus
  tuios set-workspace-name -s "$S" 2 comms
  tuios focus-window -s "$S" shell
fi

exec tuios attach "$S"

6. A hook-driven workflow

Hooks run a shell command when an event happens, with the facts in TUIOS_* variables. The full schema (all ten events, which side runs each, every variable) is in Configuration and upstream HOOKS.md. This workflow uses after-command-finished, which the daemon fires when a pane’s shell reports through OSC 133 that a command finished: when a command that ran longer than 30 seconds fails, it takes a screenshot of the pane and sends a desktop notification. It also logs every new window.

[hooks]
after-command-finished = "sh ~/.config/tuios/hooks/long-fail.sh"
after-new-window = "printf '%s %s %s\\n' \"$(date +%T)\" \"$TUIOS_SESSION_ID\" \"$TUIOS_WINDOW_NAME\" >> ~/.cache/tuios-windows.log"
#!/bin/sh
# ~/.config/tuios/hooks/long-fail.sh
# Gets TUIOS_COMMAND, TUIOS_EXIT_CODE, TUIOS_DURATION_MS, TUIOS_SESSION_ID,
# TUIOS_WINDOW_ID and TUIOS_WINDOW_NAME from the daemon.
[ -n "$TUIOS_EXIT_CODE" ] || exit 0                 # shell sent no status
[ "$TUIOS_EXIT_CODE" -ne 0 ] || exit 0              # success: nothing to do
[ "${TUIOS_DURATION_MS:-0}" -ge 30000 ] || exit 0   # quick failures are noise

TUIOS=/opt/homebrew/bin/tuios                       # full path: the daemon's PATH is not yours
dir=$HOME/Pictures/tuios/failures
mkdir -p "$dir"
out="$dir/$(date +%Y%m%d-%H%M%S)-${TUIOS_WINDOW_NAME:-pane}.png"
"$TUIOS" screenshot -s "$TUIOS_SESSION_ID" -w "$TUIOS_WINDOW_ID" --no-copy -o "$out" >/dev/null

msg="$TUIOS_WINDOW_NAME: '$TUIOS_COMMAND' failed ($TUIOS_EXIT_CODE) after $((TUIOS_DURATION_MS / 1000))s"
if command -v notify-send >/dev/null; then
  notify-send "tuios" "$msg"
elif command -v osascript >/dev/null; then
  osascript -e "display notification \"$(printf '%s' "$msg" | tr -d '\"')\" with title \"tuios\""
fi

Then load and check it:

chmod +x ~/.config/tuios/hooks/long-fail.sh
tuios list-hooks                      # the rows show whether each command was loaded
tuios list-hooks --event after-command-finished --json |
  jq '.hooks[] | {runs, last_exit_code, last_error}'

The daemon reads [hooks] only when it starts, so a change to a daemon-run hook takes effect after tuios kill-server, which ends every shell (the layout comes back from saved state with new shells). A daemon hook gets the daemon’s environment, not your shell’s, hence the full paths. And do not let a hook cause its own event: an after-new-window hook that runs tuios new-window feeds itself. Screenshots and notifications are safe.

TUIOS_COMMAND is the command line cut to 512 bytes with likely secrets masked, and TUIOS_EXIT_CODE is empty when the shell sent no status. A pane without shell integration never fires the event, and a standalone tuios with no daemon does not fire it at all.

Scripting tips: –json and jq

Almost every command takes --json. Use it whenever a script reads a result, rather than parsing the table output.

# Ids and names of every window, tab-separated
tuios list-windows -s work --json | jq -r '.windows[] | "\(.window_id)\t\(.display_name)"'

# Panes at a prompt whose last command failed
tuios list-windows -s work --json |
  jq -r '.windows[] | select(.at_prompt and (.last_exit_code // 0) != 0)
         | "\(.display_name)\t\(.last_exit_code)\t\(.last_cmdline)"'

# Ids of what you create
id=$(tuios new-window -s work job --json | jq -r .window_id)
logs=$(tuios split-window -s work vertical --name logs --json | jq -r .window_id)

# Exit code and duration of a run; does a session exist; which hooks failed
tuios run -s work -w build --json -- make lint | jq '{exit_code, duration_ms}'
tuios ls --json | jq -e 'any(.[]; .name == "work")' >/dev/null && echo yes
tuios list-hooks --json | jq '.hooks[] | select(.last_error != "")'

# React to events instead of polling
tuios subscribe -s work --types window-created | jq -c .

list-windows --json returns windows, total, focused_window_id, focused_index, current_workspace and workspace_windows. Each window has window_id, index, display_name (its name), title, workspace, focused, minimized, cwd, foreground_cmd, its geometry and agent_state, plus, for a shell with OSC 133 marks, marks_commands, at_prompt, command_seq, running_cmdline, last_cmdline, last_exit_code and last_duration_ms.

Habits that keep scripts deterministic: always pass -s SESSION; name every window you create or keep its id, and never rely on the focus; wait on events (wait-for, run) rather than sleep; make markers fresh; use --no-focus so a script does not pull the person away; close what you open. Every command is also a JSON verb on the daemon’s socket (tuios list-verbs); see Extending tuios.

Glossary

Tape
A text file of tuios commands, one per line, played back by tuios tape play, tuios tape exec or the tape manager.
Project tape
A .tuios.tape file in a project directory, written in the layout body language, run only after you review and trust it.
Capture mode
The screenshot gesture (Ctrl+b C) for picking a window, the screen or a region.
OSC 133
The terminal escape sequences a shell uses to mark its prompt and each command’s start and end; tuios run, wait-for command-finished, capture-pane --last-command and the after-command-finished hook depend on them.
Marker
A unique string a script makes a command print so that wait-for window-output can tell when it finished.
Hook
A shell command in [hooks] run on an event, with the facts in TUIOS_* variables.
