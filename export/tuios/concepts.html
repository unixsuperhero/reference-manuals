Chapter 2 tuios manual

TUIOS: Core Concepts and the Screen

The tuios mental model of daemon, sessions, workspaces and windows, its input modes, its tiling layouts, and every part of the screen from the dock and the rail to overlays, copy mode, images and the mouse.

tuiosconceptstilinginterfacemouse

This chapter explains how tuios is put together and what everything on its screen means. It starts with the object model (the daemon, sessions, workspaces, windows and panes), moves on to the input modes and the tiling layouts, and then walks the screen from the outside in: the dock, the rail, title bars and borders, the overlays, copy mode, images and the mouse. Read it once from top to bottom to build the mental model, then come back to a section when you need its details.

Every key in this chapter is the shipped default of tuios v0.8.5, read from the defaults in internal/config/userconfig.go. The leader key is Ctrl+b and the command palette is Ctrl+p. If your config.toml changes them (for example leader_key = "ctrl+a"), tuios keybinds list shows your own bindings, and tuios keybinds explain <key> tells you what one key does. The full key reference is Keybindings; the options mentioned here are in Configuration.

On macOS the defaults that use Alt are written with Opt (opt+1, opt+h). tuios reads opt+ as alt+, so the two spellings are the same key. See Keybindings for the Option-as-Alt setup that macOS terminals need.

The object model

tuios is a terminal window manager. It draws windows inside your existing terminal, the way a desktop window manager draws windows on a monitor, and it keeps them alive in a background process the way tmux does. Five nouns describe everything it manages.

daemon (one per user, per XDG_RUNTIME_DIR)
└── session "work"                    (named; many per daemon)
    ├── workspace 1                   (numbered 1-9)
    │   ├── window 3a42ab8f "editor"  (one pane each)
    │   └── window 98db8226 "build"
    ├── workspace 2
    │   └── window 5c0e1d77 "logs"
    └── scratch workspace 1000+       (the scratch terminal, see below)

The same structure as data, roughly what tuios list-windows --json and tuios list-workspaces --json describe:

session = {
  name: "work",
  current_workspace: 1,
  workspaces: [
    { number: 1, name: "1", windows: ["3a42ab8f", "98db8226"] },
    { number: 2, name: "logs", windows: ["5c0e1d77"] },
  ],
  windows: {
    "3a42ab8f": { name: "editor", title: "nvim main.go", workspace: 1, focused: true },
    "98db8226": { name: "",       title: "~/dev/api - fish", workspace: 1 },
    "5c0e1d77": { name: "logs",   title: "tail -f app.log", workspace: 2, minimized: true },
  },
}

The daemon

The daemon is a tuios process running in the background. It owns every shell process (every PTY) and runs a terminal emulator for each one, so output keeps being parsed while nobody is looking. A client, the tuios you see in your terminal, is only a viewer: it subscribes to the PTY output, draws it, and forwards your keys back.

Running plain tuios attaches to a daemon-backed session and starts the daemon first if none is running. This is the startup.daemon option, and it ships on.

tuios                     # attach to a daemon session, starting the daemon if needed
tuios daemon              # run the daemon in the foreground, for debugging
tuios kill-server         # stop the daemon and every session in it
tuios --standalone        # no daemon for this one run: the session dies with the process

Because the daemon holds the shells, closing your terminal window, losing an ssh connection or pressing Ctrl+b d (detach) leaves every program running. More than one client can attach to the same session at once, and every attached client has full control. Detach, reattach, multiple clients and resurrection after a reboot are covered in Sessions.

Inside a daemon pane TUIOS_ENV=1 is set, along with TUIOS_SESSION, TUIOS_PANE_ID and TUIOS_SOCKET. A script can test [ "$TUIOS_ENV" = 1 ] to know it runs in tuios. A --standalone tuios has no daemon and no socket.

Sessions

A session is a named, independent desktop inside the daemon: its own nine workspaces, its own windows, its own layout state. You can have many sessions and switch between them without detaching.

tuios new work            # make the session "work" and attach to it
tuios new scratch --detach
tuios ls                  # list the live sessions
tuios attach work         # attach to "work"
tuios attach              # attach to the most recent session

In the client, Ctrl+b S opens the session switcher, Ctrl+b ( and Ctrl+b ) move to the previous and next session, and N in window mode makes a new session. The rail lists every session at its top.

The most recently active session

Nearly every tuios subcommand takes -s NAME to pick its session. When you leave -s out, the command goes to the most recently active session. With one session that is always right. With several live sessions it is a guess, so scripts and agents running inside a pane should name their own session:

tuios list-windows                         # the most recently active session
tuios list-windows -s work                 # exactly "work"
tuios list-windows -s "$TUIOS_SESSION"     # the session this pane belongs to

-s omitted means “the most recently active session”. tuios attach with no name attaches to the most recent session.

A session has a name, which is its address (-s, tuios attach), and may have a display label and an accent colour, which only change how it looks:

tuios rename-session work payments        # changes the address
tuios set-session-name "Payments API"     # changes only the label
tuios set-session-accent cyan

Workspaces

Each session has nine numbered workspaces, 1 to 9. A workspace is one screen of windows, like a virtual desktop. Exactly one workspace is shown at a time; the windows on the others keep running. Each workspace keeps its own layout data (its BSP tree, its column strip, its master side and count) and its own remembered focus.

Keys Action
Alt+1 to Alt+9 Show workspace N (switch_workspace_N)
Alt+Shift+1 to 9 Move the focused window to workspace N and follow it (move_and_follow_N)
Ctrl+b w then 1 to 9 Show workspace N (workspace prefix)
Ctrl+b w then ! @ # … ( Move the focused window to workspace 1 to 9
Ctrl+b w r Rename the current workspace
Ctrl+b W Open the workspace switcher

On macOS the first two rows are Opt+1 and Opt+Shift+1. They work on a stock macOS terminal because tuios reads the composed characters back into the chord.

A workspace’s number is its identity. Its name is a label you give it, and the dock shows the name. You can also drag the workspace pills in the dock into a different order; that changes only the display order, never the numbers the keys and commands use.

tuios list-workspaces -s work
tuios select-workspace 2 -s work
tuios set-workspace-name 2 review
tuios move-window -s work 2 -w build --follow

The scratch terminal lives on workspaces numbered from 1000 up. They are not part of the 1-9 range, the session’s current workspace is never one of them, and list-windows marks their panes "scratch": true.

Windows and panes

A window is one terminal: a PTY running a program (your shell by default), drawn with a border and a title bar. Every window owns exactly one pane, the area that shows the terminal’s content. tuios uses the two words almost interchangeably: “window” when talking about the object with a title, a position and an id, “pane” when talking about the terminal content or about a tile in a layout. There is no tmux-style window that holds several panes; a split in tuios makes a second window.

Keys (window mode) Prefix chord Action
n Ctrl+b c New window
w or x Ctrl+b x Close the focused window
r Ctrl+b r Rename the focused window
Tab / Shift+Tab Ctrl+b n / p Next / previous window
1 to 9 Ctrl+b 0 to 9 Focus window N on the workspace

A new window starts in the focused pane’s working directory (appearance.new_window_inherit_cwd, default true). From a shell:

tuios new-window -s work docs --cwd ~/dev/docs --no-focus
# prints the short id and the name, for example:
# 3a42ab8f  docs

Focus

One window per workspace has the focus. It is drawn with the focused border colour, it receives your keys in terminal mode, and every window-management action (close, rename, split, zoom, swap) acts on it. Focus moves with:

Direction Window mode Terminal mode After the prefix
Left h Alt+Left Left
Down j Alt+Down Down
Up k Alt+Up Up
Right l Alt+Right Right

Directional focus goes to the nearest window that lies in that direction and faces the focused one. At the edge of a tiled layout it stays where it is. With tiling off, h and l snap the window to the left or right half instead (snap_left, snap_right); j and k always move focus. In terminal mode Alt+n and Alt+p cycle to the next and previous window (on macOS also Opt+Tab and Opt+Shift+Tab).

The prefix stays armed for half a second after a repeatable command, so Ctrl+b Left Left Left walks three panes on one prefix press (appearance.prefix_repeat_time, 0 turns it off).

tuios focus-window -s work build              # by name, on any workspace
tuios focus-window -s work --relative next
tuios focus-window -s work --direction left

appearance.focus_follows_mouse = true focuses the pane under the pointer as the mouse moves. appearance.auto_enter_terminal_on_focus (off, targeted, all) decides whether a keyboard focus change also starts typing in the pane.

Floating and tiled windows

A window is either tiled or floating.

  • A tiled window has its rectangle chosen by the layout (BSP, master-stack or scrolling). You never place it by hand; you split, swap, rotate and resize the layout.
  • A floating window has a position and size of its own. You drag it, resize it by its edges and stack it over other windows, like a window on a desktop. Floating windows draw above the tiles.

Tiling is a per-session switch: with tiling on, new windows join the layout; with tiling off, every window floats. New sessions start tiled (startup.tiled = true).

Keys Action
t (window mode), Ctrl+b Space Toggle tiling for the session
Palette: “Toggle floating” Lift only the focused window out of the layout, or put it back

“Toggle floating” leaves the rest of the layout tiled and shows the dock message Window: floating or Window: tiled. A popup and a scratch pane are always floating and cannot be tiled.

With tiling off, the snap keys place a floating window:

Keys Action
h / l Snap to the left / right half
f Snap to the full screen
u Unsnap the window from its snapped position
Ctrl+b L 1 to 4 Snap to a corner quarter

With tiling on, f, u and the corner snaps do nothing except say that they need tiling off, because the tiler owns the rectangles.

Minimize, zoom and fullscreen

Minimizing hides a window without closing it. Its program keeps running and it shows up as an entry in the middle of the dock.

Keys Action
m (window mode) Minimize the focused window
M Restore every minimized window
Shift+1 to Shift+9 (also ! … () Restore minimized window N
Ctrl+b m m Minimize the focused window (minimize prefix)
Ctrl+b m 1 to 9 Restore minimized window N
Ctrl+b m M Restore all
Click a dock entry Restore that window 
tuios set-window -s work -w build --minimize
tuios set-window -s work -w build --restore

Zooming is tuios’s maximize. A zoomed pane takes 95% of the screen by default, centred over the layout, and the dock’s mode pill gains a Z. The layout underneath is untouched, and zoom again puts the pane back in its tile.

Keys Action
z (window mode) Toggle zoom on the focused pane
Ctrl+b z Toggle zoom (prefix_fullscreen; the dock says ZOOM)
The third title-bar button Toggle zoom 
[appearance]
zoom_size = 100            # percent of the screen; 100 is true fullscreen (default 95)
zoom_max_width = 120       # cap the zoom box at 120 columns, centred (0 = no cap)
zoom_follows_focus = true  # moving focus hands the zoom to the newly focused pane
zoom_animation = true      # slide between the tile and the zoom box

A zoomed pane cannot be dragged or resized. A fullscreen zoom hides the shared borders.

“Fullscreen” has two meanings. f with tiling off is a snap: it moves a floating window to fill the screen. z or Ctrl+b z is a zoom, which works in every layout and leaves the layout alone.

Window names and program titles

A window has two labels:

  • Its name, which you give it with r, Ctrl+b r, tuios new-window NAME, tuios set-window --name or tuios split-window --name.
  • Its title, which the program inside sets with the terminal title escape (a shell typically sets ~/dev/api - fish, an editor its file name).

The name wins. The title bar, the dock, the rail, the palette and list-windows show the name when there is one and the program’s title otherwise. Clearing the name brings the title back:

tuios set-window -s work -w build --name "api tests"
tuios set-window -s work -w build --name ""     # back to the program's title

The name is also an address: -w build finds the window you named build, whatever its program calls itself. appearance.window_title_format decides what the title bar prints, with the tokens {title} (the name or the program’s title), {index} (the window’s 1-based position on its workspace, the number the digit keys use) and {cwd}:

[appearance]
window_title_format = "{index}: {title}"
window_title_position = "top"   # top, bottom or hidden (default top)

Window ids, indexes and prefixes

Every window has a UUID, such as 98db8226-1829-468e-89a8-41a2baa0ddab. Inside a pane it is TUIOS_PANE_ID (and the same value in TUIOS_WINDOW_ID). Listings and command output show the first eight characters, 98db8226.

-w accepts, in this order of precedence:

Form Example Notes
Full UUID -w 98db8226-1829-468e-89a8-41a2baa0ddab Always exact
Index -w 2 All digits: the index list-windows prints. It shifts when an earlier window closes
Exact name -w build A name you gave, not a program title
Unique id prefix -w 98db Any unambiguous prefix of the UUID

A name beats a prefix, so a window named db is never mistaken for a window whose id starts with db. An ambiguous name or prefix is an error that lists the candidates; tuios never guesses. Scripts should hold the id or the name, never the index.

id=$(tuios new-window -s work worker --print-id)
tuios send-text -s work -w "$id" 'make test
'

Popups, the scratch terminal and picture in picture

Three window kinds sit outside the normal layout.

  • A popup is a floating pane centred over the layout that closes when its command exits: tuios popup -- fzf. It is never tiled, never in the window cycle and cannot join multifocus. See Overlays.
  • The scratch terminal (Ctrl+b g) is a small layout of panes in a box over the current workspace. The key shows and hides the box; the shells keep running. Inside the box the window keys act on its panes. [scratch] sets the box size. See Sessions.
  • Picture in picture (p in window mode) pins the focused pane as a small live copy in a corner of the screen. p again, on any pane, unpins it, and a click on the view focuses that pane. It belongs to your client only. [pip] sets the size and corner.
tuios popup -s work --width 60 --height 20 -- gum choose one two three
tuios pip -s work agent     # pin the pane named agent
tuios pip -s work --off

Modes

tuios is modal, like vim. The same key means one thing when you are managing windows and another when you are typing into a shell. Knowing which mode you are in, and how to leave it, is the single most important habit.

Window management mode

In window management mode (window mode for short, WM in some docs) the keyboard drives tuios. n makes a window, h moves focus left, z zooms, and nothing reaches the shells. A fresh session starts here unless startup.start_in_terminal_mode = true.

Terminal mode

In terminal mode every key goes to the program in the focused pane, except the few that tuios keeps for itself:

Keys Why tuios keeps them
The leader, Ctrl+b Starts a prefix chord
Ctrl+p, Alt+Space [keybindings.global]: the palette and the launcher, in both modes
Alt+arrows Move focus between panes
Alt+n, Alt+p Next and previous window
Alt+Esc Leave terminal mode
Shift+Up, Shift+Down Scroll the pane’s scrollback
Ctrl+Shift+v, Super+v Paste from the host clipboard
Alt+1 … Alt+9 Switch workspace

A bare Esc in terminal mode goes to the program, as vim needs. To send the leader itself to the program, press it twice: Ctrl+b Ctrl+b.

The global and terminal-mode bindings take keys away from your shell: Ctrl+p is history-back in many shells and Alt+Left/Right are word motions in readline, fish and zsh. To give a key back, set its action to [] or run tuios keybinds free <key>:

[keybindings.global]
command_palette = ["ctrl+shift+p"]

[keybindings.terminal_mode]
terminal_focus_left = []
terminal_focus_right = []

Ctrl+b d detaches in a daemon session. Only in a standalone session, where there is nothing to detach from, does it drop you back to window mode. Use Ctrl+b Esc to change mode.

Prefix mode and the leader key

The leader key (Ctrl+b, keybindings.leader_key) arms prefix mode for one following key, the way tmux’s prefix does. It works from both modes, which is why every important action has a prefix chord: you can reach it while typing in a shell without leaving terminal mode.

While the prefix is armed a badge reading PREFIX | <time> lights up, and if you wait 500 ms the which-key panel opens with every key you can press next (see Which-key). In terminal mode, a key that is not bound after the prefix is typed into the focused pane.

The leftmost cell of the dock is the mode pill. Its colour and its glyph tell you who has the keyboard. With the Nerd Font glyph set the icons are a window, a terminal and a grid; with an ASCII glyph set they are the letters below.

BSP tiling

BSP (binary space partitioning) is the default tiling layout. It is the model bspwm uses: the screen is a binary tree, every internal node is a split into two halves, and every leaf is one window. Upstream keeps its tiling guide on the docs site at https://tuios.dev/docs/bsp-tiling; this section describes the behaviour of v0.8.5 as the source implements it.

The tree

Each workspace has its own BSP tree. A leaf holds one window. An internal node holds a split type and a split ratio:

  • A vertical split puts its two children side by side, with a vertical divider between them (left/right).
  • A horizontal split stacks its children, with a horizontal divider (top/bottom).
  • The ratio is where the divider sits, from 0.0 to 1.0. Every new split starts at 0.5, the middle.
workspace 1, three windows                tree

+-------------+-------------+             vertical 0.5
|             |   B         |             ├── A
|   A         +-------------+             └── horizontal 0.5
|             |   C         |                 ├── B
+-------------+-------------+                 └── C

As data:

tree = {
  split: "vertical", ratio: 0.5,
  left:  { window: "A" },
  right: { split: "horizontal", ratio: 0.5,
           left: { window: "B" }, right: { window: "C" } },
}

When a window opens it splits the focused pane: the focused leaf becomes an internal node, the old window becomes its first child and the new window its second. When a window closes, its sibling takes over the parent’s whole space, so the tree collapses by one level.

Turning tiling on and off

Keys Action
t (window mode) Toggle tiling
Ctrl+b Space Toggle tiling
Ctrl+b t t Toggle tiling (window sub-prefix)
Palette: “Layout: BSP tiling” Use BSP, turning tiling on if it was off 
tuios set-layout -s work --tiling true
tuios run-command -s work ToggleTiling      # also EnableTiling, DisableTiling

Turning tiling off leaves every window floating where it was. Turning it on again retiles the workspace. The layout mode (BSP, master-stack, scrolling) is remembered across the toggle.

startup.tiled = true: new sessions start tiled. startup.layout = "bsp": the mode a new session starts in.

Insertion schemes

When nothing says which way to split, the workspace’s tiling scheme decides the axis of the next automatic split:

Scheme How it picks the axis
spiral (default) Alternates by the depth of the window being split, bspwm style, which spirals inward
longest_side Splits across the focused window’s longer side
alternate Alternates by the total number of splits in the tree
smart_split From the focused window’s shape: wider than twice its height splits side by side, taller than wide stacks, otherwise depth parity 
[appearance]
tiling_scheme = "longest_side"   # the scheme a NEW workspace starts with

The scheme is per workspace. Change the one on screen from the palette (“Cycle tiling scheme”, “Set tiling scheme: spiral”, and so on) or bind the actions cycle_tiling_scheme and set_tiling_scheme_spiral, _longest_side, _alternate, _smart_split, which have no default key.

The mode pill always shows the axis of the next split: V for side by side, H for stacked. “Smart split” in the palette (tiling on) splits the focused pane once, on the axis its aspect ratio suggests.

Splitting on purpose

An explicit split chooses the axis for you:

Keys (window mode) Prefix chord Action
| or \ Ctrl+b | split_vertical: new window to the right (left/right)
- Ctrl+b - split_horizontal: new window below (top/bottom) 
tuios split-window -s work vertical
tuios split-window -s work horizontal -w build --name logs
tuios split-window -s work vertical --json | jq -r .window_id

The right-click pane menu has “Split right” and “Split down” for the same two splits.

tmux users: tuios names the split after the divider, like vim. A “vertical” split draws a vertical line and gives you two panes side by side.

Preselection

Preselection says where the next window goes, relative to the focused pane, before you open it. Press a preselect key, then make a window with n, Ctrl+b c or any other new-window command. The new window lands on that side and the preselection is used up.

Keys (window mode) macOS Places the next window
Alt+h Opt+h Left of the focused pane (vertical split, new window first)
Alt+l Opt+l Right of it (vertical split, new window second)
Alt+k Opt+k Above it (horizontal split, new window first)
Alt+j Opt+j Below it (horizontal split, new window second)

While a preselection is pending, the mode pill shows its axis (V for left and right, H for up and down) instead of the scheme’s guess. A preselection belongs to the pane focused when you set it.

Example: an editor with a narrow terminal on its left. Focus the editor, press Alt+h, then n. The shell opens to the left of the editor. Press Ctrl+b L 7 on the editor to give it 70% of the width.

In a tape script the Preselect command does the same (see Automation).

Resizing and split ratios

Every resize in BSP is written into the ratios of the tree, so it survives a retile, a new window elsewhere, and a reattach.

Keys (window mode) Action
> / < Move the focused pane’s right edge right / left (grow / shrink width)
. Move the focused pane’s left edge left (grow width from the left)
} / { Move the bottom edge down / up (grow / shrink height)
] / [ Move the top edge (grow / shrink height from the top)
Ctrl+b L 5 … 9 Set the focused pane’s width to 50% … 90%
Ctrl+b L Shift+5 … 9 Set its height to 50% … 90%
Drag a divider Move that one divider

The percentage actions exist for every step from 10 to 90 (resize_width_10 … resize_width_90, resize_height_10 …); only 50-90 have default keys. The layout still enforces a minimum pane size, the gap and the neighbours, so you get the requested size wherever the layout allows it. Dragging a divider moves only the split that owns that edge, so unrelated panes stay still.

Swapping

Swapping exchanges two windows’ places in the tree. The tree’s shape and its ratios stay; only which window sits in which leaf changes.

L or Ctrl+Right Swap right
K or Ctrl+Up Swap up
J or Ctrl+Down Swap down

Gaps and shared borders

Two settings change the space between tiles:

[appearance]
gap = 1               # cells of empty ground between neighbouring panes (default 0)
shared_borders = true # one divider line between adjacent panes, tmux style (default false)
  • gap leaves empty cells between panes, in every tiling mode.
  • shared_borders drops each pane’s own border box and draws one separator between neighbours, which gives each pane two more columns and rows. It applies to BSP and master-stack only; the scrolling layout always draws its own borders. The palette has “Toggle shared borders”, and the flag tuios --shared-borders turns it on for one run.

gap, master_ratio, scroll_column_width and shared_borders decide how many cells a pane gets, so they are settled across the session: change one on any client and every client attached to the session follows. Purely visual settings (theme, border style, glyphs, dimming) stay per client.

Scrolling (niri-style)

The scrolling layout, modelled on the niri window manager, arranges windows as columns on a strip wider than the screen; the screen is a viewport onto the strip. A new window becomes a new column right after the focused one and the viewport scrolls to it, instead of every pane shrinking to make room. A column can hold several windows stacked vertically, sharing its height evenly.

The rail

The rail is the sidebar: a column of sessions, terminals, files, git state and agents, on by default on the right edge (appearance.sidebar.enabled, appearance.sidebar.position: left, right or hidden). The docs call it both “the rail” and “the sidebar”; they are the same thing.

The @ state filter

A leading @ token keeps only the panes whose agent is in a given state, and drops every static command. It is resolved by prefix, so one letter is enough:

Token Keeps panes that are
@ alone running an agent at all
@a, @attention waiting on input or errored (what the rail marks as needing you)
@w, @working working
@n, @needs_input waiting on input
@d, @done done
@i, @idle idle
@e, @errored errored

Text after the token is matched as usual, so @a api finds the panes needing you whose name matches api. An @ naming no state matches nothing rather than silently matching everything.

Dialogs

A dialog is a small centred question. tuios uses them for anything destructive or anything that needs a name:

Popups

A popup is a floating pane centred over the layout for one command. It closes when the command exits, is never tiled, and is not in the window cycle.

tuios popup -s work -- htop                              # q closes it
tuios popup -s work --width 90% --height 80% -- lazygit
file=$(tuios popup -s work --capture-stdout -- fzf)      # use the answer
tuios popup -s work --wait -- gum confirm "Deploy?" && ./deploy.sh

The default size is 80% by 60% of the pane region. A popup closed by hand exits 130. A [[keybindings.command]] entry of type = "popup" binds one to a key (see Keybindings).

The review overlay and the diff view

Ctrl+b v opens the review overlay on the focused pane: the git diff of the changes under that pane’s directory, over the whole screen. It exists for reviewing what a coding agent changed without leaving tuios, and for sending the agent notes on specific lines. With no git repository under the pane, the dock says so and nothing opens. It is also reached with v on an Inbox item or a rail agent row.

The layout is a file list on the left and the diff view of the selected file on the right. The diff view (internal/diffview) colours code by file type in the active theme’s colours, puts added and removed lines on green and red grounds, marks the words that changed inside a changed line, and can show the old and new sides next to each other when the column is wide enough (about 120 columns). Copy mode, scrollback and the clipboard

Scrollback

Every pane keeps a scrollback of lines that scrolled off its top: appearance.scrollback_lines, 10,000 by default (100 to 1,000,000), kept on both sides of the daemon socket. You can look back through it three ways:

Way How What it is
Wheel Turn the wheel over a pane The view scrolls; typing, or scrolling back to the bottom, returns to live output
Keys Shift+Up / Shift+Down in terminal mode Scroll into the scrollback and back down
Copy mode Ctrl+b [ Vim-style cursor, search and selection

The wheel scrolls appearance.scroll_lines lines per notch (default 3). It borrows copy mode’s machinery silently: no notification, no change to the mode pill, no keys to learn. A program that turned on mouse tracking (vim, less, htop) gets the wheel itself instead, and a pane with no history is left alone.

[appearance]
scrollback_lines = 50000
scroll_lines = 5

The palette’s “Edit scrollback in $EDITOR” opens the pane’s scrollback in your editor.

Ctrl+b [ (or palette “Enter copy mode”) starts copy mode on the focused pane. The copy cursor starts on the terminal cursor, usually the prompt line, as in tmux; appearance.selection.copy_entry = "center" starts it on the middle row. The mode pill shows the cursor’s row:col and the dock shows copy mode’s key help. A digit prefix repeats a motion (5j, 10G).

The clipboard

A copy goes to your terminal’s clipboard with OSC 52, and on a local client also through the system clipboard tool. Programs inside panes can set the clipboard with OSC 52 too; appearance.selection.osc52_write decides whether they may:

Value Programs may set the clipboard
focused (default) From the focused pane; the dock says so when the text holds a line break or control character. Other panes wait for you to allow it
ask Only after you allow it, from any pane
on Always
off Never

Whatever the mode, a pane keeps its own copy, so the program that set it can read it back. Some terminals cut long OSC 52 writes; multi copy mode warns above 100 KB.

Images

tuios passes images from programs in panes through to your terminal, clipped to the pane like text. What you see depends on what your host terminal supports, because every client draws images for its own terminal.

Program writes Host has kitty graphics (kitty, Ghostty, WezTerm) Host has sixel only (foot, xterm, mlterm, Konsole, Windows Terminal) Host has neither
Kitty graphics (kitten icat, mpv --vo=kitty, chafa, timg, yazi) Drawn Not drawn Not drawn
Kitty Unicode placeholders Drawn where the terminal is known to support them Not drawn Not drawn
Sixel (img2sixel, lsix, chafa) Drawn, converted to a kitty image Drawn as sixel A dim box reading image

Kitty graphics

Kitty graphics are the best supported path. tuios intercepts each image, works out where the program’s placement lands on your screen from the pane’s position and scroll, and re-emits it there. Image ids are reused across frames and output is batched with the render cycle inside synchronized output (mode 2026), so video plays without flicker: mpv --vo=kitty works in both its shared-memory and base64 modes. A program’s animation frame edits (a=f) are forwarded as rectangles rather than whole bitmaps.

  • Overlap. A window drawn over part of an image crops the image to what is still clear, in up to several rectangles, instead of hiding it.
  • Resizes and full-screen overlays hide placed images while they last, because the host paints images over the finished frame.
  • Unicode placeholders (the image lives in special text cells) scroll and clip exactly like text. tuios asks the terminal who it is (XTVERSION) and keeps placeholder cells only for terminals known to draw them; appearance.kitty_placeholders (auto, on, off) or TUIOS_KITTY_PLACEHOLDERS=1/0 overrides that. They need a truecolor host and do not show in tuios-web.
  • File transmission (t=f, t=t, t=s): a path a program sends is checked before anything reads it (absolute, regular file, your own, t=s inside /dev/shm), and a program on another machine is told to send bytes instead.

Sixel

A sixel image has no id and no way to be cropped, so tuios does what a sixel terminal does internally: it decodes the image and marks every cell it covers. On each frame it finds the marked cells that are actually visible and sends just that part, as sixel on a sixel host or as a kitty image on a kitty host. The picture therefore scrolls into the scrollback with its cells and disappears when text is written over it or it is cleared.

A pane is told it can draw sixel only when its picture will really be shown, so tools such as chafa, timg and yazi fall back to text on a plain terminal. TUIOS_SIXEL_GRAPHICS=1/0 overrides detection. A pane holds at most 16 MiB and 4096 sixel images; copies, searches, capture-pane and hints see blanks where image cells are.

The kitty text sizing protocol (OSC 66) passes through but is experimental, with known issues in the scrollback and when windows move.

Screenshots

tuios renders screenshots from a pane’s own cells, so colours, styles and links are exact and no pixels are scraped from your terminal. The files are written by the daemon, so a screenshot works on a detached session.

Capture mode

Ctrl+b C enters capture mode, which owns the keyboard and mouse until it ends. Hovering lifts the window under the pointer so you can see what a click would capture.

Input Captures
Click a window That window
Drag A region of the screen
f The full screen
Enter / Space The highlighted window
Tab / Shift+Tab (also arrows, h j k l) Move the highlight to the next / previous window
Esc, q, Ctrl+c Cancel

Over an open panel (the palette, settings, a menu, the Inbox) capture mode keeps the panel in the picture; then Enter, f or a click takes the whole screen and a drag takes a region.

After a capture the preview panel opens (screenshot.preview, default true): Enter done, c copy, o open, r retake, Esc discard. The palette has “Screenshot this window”, “Screenshot a region” and “Screenshot the screen”, and the pane’s context menu has “Screenshot this window”.

From a shell

tuios screenshot                                   # focused window, PNG in screenshot.directory
tuios screenshot -s work -w build                  # a named window; detached is fine
tuios screenshot --scrollback --lines 200          # with history above the screen
tuios screenshot --format svg --out demo.svg
tuios screenshot --theme catppuccin_mocha          # re-render in another palette
tuios run-command -s work Screenshot

Formats are png, svg, ansi, html and txt. PNG and SVG carry a frame (padding, a background wash from your theme, rounded corners, a shadow and a title bar with window controls); ansi and txt are the bare stream.

[screenshot]
format = "png"              # png, svg, ansi, html, txt
directory = "~/Pictures/tuios"
frame = "window"            # window, plain, none
padding = 48                # px, 0-128
radius = 10                 # px, 0-32
shadow = true
controls = "auto"           # auto (macOS lights), macos, glyphs, none
scale = 2                   # PNG raster scale, 1-4
copy = true                 # try to put the image on the clipboard

With no theme set, basic and indexed colours fall back to the xterm defaults, because only your terminal knows its own palette. The result says so. Use --theme to render in a named palette.

The performance model

tuios is built to cost nothing while nothing happens. Upstream measures this in https://github.com/Gaurav-Gosain/tuios/blob/v0.8.5/docs/perf.md.

  • Event-driven rendering. Each pane’s PTY reader signals the UI through a channel when output arrives. There is no fixed-rate redraw of terminal content; a frame is drawn only when output, input or an animation changed something, and an unchanged frame is skipped.
  • An idle maintenance tick runs at a low rate (10 per second) and skips its scans behind a cheap check, so idle shells cost a few hundred nanoseconds per tick and send nothing to your terminal. The measured target is zero timer-driven renders and idle CPU under about 0.5% with the rail on.
  • Dock components arm no timer unless one is configured to poll. The clock redraws once a second only when its format shows seconds.
  • Culling and caching. Off-screen and minimized panes are not rendered; unchanged windows reuse their cached layer; styles come from an LRU cache; buffers are pooled. Unfocused panes use the emulator’s fast render unless dim_unfocused needs every cell.
  • Synchronized output. Frames and image data go out inside mode 2026, so your terminal never shows half a frame.
[appearance]
max_fps = 60     # 0 means 60; otherwise 10 to 120
motion = "basic" # none, basic or full: how much animates (default full)

The daemon and the client split the work: the daemon parses every pane’s output all the time (so nothing is lost while detached), and the client only draws what is on screen.
