Chapter 4 tuios manual

TUIOS: Configuration, Themes, Glyphs and Hooks

Where the tuios config file lives, every table and key in config.toml, how settings reload, and how themes, glyph sets, sounds and hooks are written and selected.

tuiosconfigthemeshooksreference

tuios reads one TOML file, config.toml, and two directories of JSON files beside it: themes/ for colour and glyphs/ for shape. Almost every scalar setting can also be changed while tuios runs, from the settings page or with tuios set-config, and the running client writes the change back to the file. This chapter is the complete reference for that file: where it lives, how it is loaded and reloaded, every table and key with its type and default, and the theme, glyph set, sound and hook mechanisms that hang off it. Keybindings have their own chapter, Keybindings.

Where the configuration lives

The config file

tuios finds its files with the XDG base directory rules, through the github.com/adrg/xdg library. The config file is tuios/config.toml under the config home:

Platform Default path
Linux, BSD ~/.config/tuios/config.toml
macOS ~/Library/Application Support/tuios/config.toml
Windows %LOCALAPPDATA%\tuios\config.toml
Any, with XDG_CONFIG_HOME set $XDG_CONFIG_HOME/tuios/config.toml

When tuios loads the file, it searches the config home first and then the system config directories (XDG_CONFIG_DIRS). When no file exists, it writes a complete default file at the config home path and uses it. When it saves, it always writes to the config home path.

The path is the one thing you never have to guess:

tuios config path
/Users/you/Library/Application Support/tuios/config.toml

On macOS, the default is under ~/Library/Application Support, not ~/.config. To keep your dotfiles in ~/.config, export XDG_CONFIG_HOME="$HOME/.config" in your shell profile before you start the daemon. Then tuios config path prints ~/.config/tuios/config.toml.

The directories beside it

Path (under the config home) Holds Read
tuios/config.toml All settings At start, and again on every save
tuios/themes/*.json Custom themes At start, on tuios list-themes, and when an unknown id is selected
tuios/glyphs/*.json Custom glyph sets Whenever a set is looked up
tuios/layouts/ Saved layout templates (tuios layout) On demand
tuios/authorized_keys Keys tuios ssh accepts When the SSH server starts

Only files directly in themes/ and glyphs/ are read. Subdirectories are ignored. tuios list-themes and tuios list-glyphs print the real directory on their last line:

tuios list-themes --filter nord
  nord        nord_light

2 of 342 registered themes.

active: (none) (default)
themes dir: /home/you/.config/tuios/themes

Scripts that hooks and dock components run can live anywhere. The examples in this manual put them in ~/.config/tuios/hooks/ and ~/.config/tuios/dock/, which is a convention, not a requirement.

The first file

The first time tuios starts without a file, it writes one with every key at its default and a comment header that says where the file is and that tuios watches it. tuios config reset writes the same file again, after it asks:

tuios config reset
Are you sure you want to reset to defaults? (yes/no):

The tuios config commands

Command What it does
tuios config path Print the path of the config file.
tuios config edit Open the file in $EDITOR, then $VISUAL, then the first of vim, vi, nano and emacs that is installed.
tuios config reset Overwrite the file with the defaults, after a yes/no prompt.
tuios config apply Tell the running daemon to apply the file now, including changes that give panes or other machines more than they had. Refused from inside a tuios pane. 
EDITOR=nvim tuios config edit

tuios config apply exists because of one rule. The daemon follows the file at once when a change gives less, such as [agents.permissions] mode = "strict" or a shorter allow list in [hosts]. A change that gives more waits, because a process inside a pane can write the file. You apply it from a terminal that is not a tuios pane:

# in a plain terminal, not a tuios pane
tuios config apply

There is no tuios config validate in v0.8.5. tuios validates the file every time it loads it. See Checking a config.

Checking a config

A config file can have errors and warnings.

  • An error is a value tuios cannot use. At startup, tuios prints each error as Config error in [SECTION]: KEY: MESSAGE and stops with configuration has N error(s), please fix and restart. During a session, a save with an error is not applied: the running settings stay, and the dock shows Config not reloaded: ....
  • A warning is a value tuios can work around, such as an unknown sound_mode, an unknown grant name, or a #RRGGBB field that is not a colour. tuios uses the default for that key and shows the warning inside the TUI, because text printed before the alternate screen opens is erased by the first frame.

Several commands check one part of the file each:

Command What it checks
tuios keybinds doctor Every key tuios cannot read (key_problems), keys bound twice, keys tuios takes from the pane
tuios list-hooks Every hook command, how many times it ran, its last exit code and error
tuios list-dock-components Every dock cell, whether it drew, and why a custom one failed
tuios list-glyphs ID --json Roles a glyph set named and did not get (problems)
tuios list-themes ID --json Colours that fail contrast on the theme’s background (palette.illegible)
tuios hosts Hosts that are ignored, and why
tuios pane-grants The grants a pane holds, and whether a permission change is waiting 
tuios keybinds doctor --json | jq -r '.key_problems[]?'
tuios list-hooks --json | jq '.hooks[] | select(.last_error != "")'

File format

The file is TOML. Each feature is a table, and a few tables have sub-tables:

[appearance]
theme = "catppuccin_mocha"
gap = 1

[appearance.sidebar]
position = "left"
width = 28

[notifications.agent.states]
idle = false

A setting’s path is its table names and key joined with dots: appearance.sidebar.width, notifications.agent.states.idle. The CLI and the settings page use the same paths.

Four rules decide how a value you leave out is read:

  1. A missing key takes its default. Most toggles are stored so that “not written” and “written as false” are different, and a missing key gets the documented default.
  2. A missing list and an empty list differ. In [dock], right = [] draws nothing on the right, while leaving right out draws the default components. In [keybindings.*], an action set to [] has no key, while an action left out gets its default keys.
  3. [startup] tiled and daemon have no fill-in. They default to true in a new file, but a file that does not name them reads them as false. An older file therefore keeps the floating, standalone behaviour it had.
  4. Empty strings often mean “follow something else”. For example, an empty appearance.pane_background follows appearance.background, and an empty notifications.mail.dock follows notifications.agent.dock.

Every change you make on the settings page, and every tuios set-config with a client attached, rewrites the whole file from tuios’s in-memory config. Your comments, your key order and your blank lines are not kept. Keep an annotated copy elsewhere (for example in a dotfiles repository) if you care about them, or make all your changes in the file and not in the app.

Precedence: flags, environment and the file

A value comes from the first of these that sets it:

  1. A runtime change in the session: the settings page, tuios set-config, or a tape’s SetConfig. These also write the file, so they persist.
  2. A command-line flag of the tuios command that starts the client.
  3. The config file.
  4. The built-in default.

A command-line flag applies to the client it starts and is not written to the file. Bare tuios and tuios attach take the same appearance flags. The flags that override config keys:

What reloads and what needs a restart

tuios watches the config file’s directory, so it sees a save from any editor, including editors that write a temporary file and rename it. It waits 200 ms after the last event of a save, then reads the file once. A file that does not parse or validate changes nothing. The command palette also has a Reload config entry that does the same thing on demand.

Different parts of the file are owned by different processes, so they reload in different ways:

Part of the file When a change applies
[appearance] and all its sub-tables, themes, glyph sets, backgrounds On save, in every attached client
[dock], including [dock.custom.*] On save; custom components restart
[spotlight], [hints], [screenshot], [scratch], [pip], [notifications.*] On save
[keybindings.*] In the next client: detach and attach again. tuios keybinds unbind and free apply at once
[[keybindings.command]] The palette row changes on save; the key works in the next client
[startup] When a new session starts. A running session keeps its own layout and mode
[hooks], daemon side When the daemon starts. Run tuios kill-server after a change
[hooks], client side When the client starts
[daemon] persist_scrollback*, window_size When the daemon starts. set-config daemon.window_size changes one session at once
[agents.approvals], [agents.queue], [agents] herdr_protocol On save, for the next prompt, message or pane
[agents.permissions], [hosts] On save when the change gives less; with tuios config apply or a daemon restart when it gives more
[agents.recap] test_patterns on save; mode and away when the client loads the config
[tape] On the next directory change

Example: watch a change land

Open the file in one pane and the session in another. Change the gap and save:

[appearance]
gap = 2

Within a fraction of a second the panes retile with two cells between them. Now break the file (delete a closing quote) and save again. The layout stays as it was and the dock shows Config not reloaded: with the parse error.

Reading and changing options at runtime

Which options are settable

Every scalar option (a bool, an int or a string) is in tuios’s option registry. The registry is the single list that tuios list-options, tuios get-config, tuios set-config, the tape SetConfig command and the settings page all use, and a test fails the build if an option is missing from one of them. In v0.8.5 the registry has 196 paths.

Tables, lists and maps are not scalar, so they are not in the registry. You change them only in the file:

  • [dock] region lists and [dock.custom.*] (only dock.clock.format is in the registry)
  • [hooks]
  • [keybindings.*], [[keybindings.command]], [[keybindings.copy_pipe]]
  • [appearance.sidebar.agent_row]
  • [hosts.*] and [tailscale]
  • [agents] and all its sub-tables
  • [notifications.agent.sounds] (the cue file paths)
  • hints.patterns, daemon.agent_binaries, daemon.respond_from_shell

Several of these are excluded on purpose: a process in a pane can call tuios set-config, so nothing that decides what a pane may do is reachable through it.

tuios list-options

tuios list-options                         # everything, grouped by section
tuios list-options --section sidebar       # one group
tuios list-options appearance.selection.   # one path prefix
tuios list-options --search "pane bg"      # fuzzy search, best first
tuios list-options --json | jq -r '.options[].path'

Each JSON entry has path, type, section, description, default, and when they apply accepted, min, max and deprecated:

{
  "path": "appearance.gap",
  "type": "int",
  "section": "appearance",
  "description": "Cells of empty ground kept between two neighbouring tiled panes",
  "default": "0",
  "min": 0,
  "max": 8
}

tuios get-config

get-config reads the value in effect for a session. A path that exists always reads, even when nothing set it. --json adds where the value came from: session (set on this session), config (the daemon’s file, for daemon.window_size only) or default.

tuios get-config border_style
tuios get-config appearance.sidebar.position --json
{
  "default": "right",
  "key": "appearance.sidebar.position",
  "option_type": "string",
  "source": "default",
  "type": "option",
  "value": "right"
}

A notifications.mail key that is not set reads as what it follows:

tuios get-config notifications.mail.dock
(follows notifications.agent.dock)

tuios set-config

set-config PATH VALUE validates the path and the value, applies the value to the session, and, when a client is attached, writes the file the way the settings page does. With nobody attached, the value applies on the next attach.

tuios set-config appearance.theme gruvbox_dark
tuios set-config border_style thick          # an [appearance] key also answers to its bare name
tuios set-config appearance.sidebar.width 30
tuios set-config -s work dock_background '#11111b'
tuios set-config appearance.sidebar.background ''   # empty: follow appearance.background again

The value is checked against the option:

Option kind Accepted value
bool true or false
int A number inside the option’s range
Closed set One of the accepted values
Colour #RRGGBB, one of the option’s keywords, or empty to clear
Theme (appearance.theme) A registered theme id. The themes directory is read again first, so a file you just wrote is found
Glyph set (appearance.glyphs) A registered set id. The glyphs directory is read again first
Box size (scratch.width, scratch.height) Cells (100) or a percent (80%)

A path that does not exist is refused, never recorded:

tuios set-config appearance.sidebar.wdith 30

The error is no such option, with a did-you-mean suggestion (here appearance.sidebar.width) and the full list of valid paths in the JSON error, so a script can correct itself without a second call.

The result reports applied: whether an attached client put the change on screen. When it is false, reason says that nobody is attached or that the client refused it.

There is no undo. Record the old value before you change one from a script:

old=$(tuios get-config appearance.theme --json | jq -r .value)
tuios set-config appearance.theme nord
# ... later
[ -n "$old" ] && tuios set-config appearance.theme "$old"

Three options have an empty default but no empty value in their accepted set, so set-config cannot put them back to the default once changed: appearance.sidebar_position, appearance.whichkey_position and notifications.agent.sound_mode. Delete the key from the file instead.

The settings page

The settings page is the same registry as a set of tabs. Open it with Ctrl+b , (the leader, then comma), with , in window mode, or from the command palette. If you changed your leader, as in leader_key = "ctrl+a", use that key instead.

The page has fourteen tabs: Appearance, Backgrounds, Sidebar, Selection, Dock, Behavior, Startup, Advanced, Spotlight, Daemon, Tape, Screenshot, Saver and Hosts.

Key On the settings page
Up, Down Move between rows (wraps at the ends)
Left, Right Change the value
Tab, ] Next tab
1 to 9 Go to that tab
/ Search every tab by name, key, current value or description
Backspace Reset the row to its default
Ctrl+z Undo the last change
Esc Clear the search, then close
  • A bool row flips, an enum row cycles, and an int row has a number editor; a percent row draws a gauge.
  • A colour row opens a picker seeded with the colour in use. Backgrounds rows also offer off and theme, and x clears a surface so it follows the All surfaces row again.
  • The Theme row opens the searchable theme picker with a swatch per theme. Cancelling restores the theme you had when you opened it.
  • The Glyph set row, under Theme, opens a picker that draws each set’s own corner, controls and rail marks, and applies the set as you move.
  • Dock, Components is an editor for the three region lists: shifted arrows move a component (and carry it into the next region off the end), Enter takes one off the bar or puts it back, u undoes this session’s edits and r restores the defaults.

Every change applies at once and is saved to the file. A client that is not allowed to write the file, such as some remote clients, applies the change to its session and says once that it did not save it.

The [appearance] table

[appearance] is the largest table: everything about how tuios looks and how the mouse and the panes behave. Every key in it is settable at runtime, and every key also answers to its bare name in tuios set-config (set-config gap 1 is set-config appearance.gap 1). The tables below are generated from the option registry of v0.8.5, so the types, defaults and value sets are exact.

Theme, glyphs and accent colours

Key Type Default Meaning
theme string (empty) Colour theme name. Empty keeps your terminal’s own colours.
glyphs string default Chrome glyph set: the characters the border, controls, rules and rail marks are drawn with.
border_focused_color string (empty) Hex colour overriding the focused pane’s border, e.g. #89b4fa.
border_unfocused_color string (empty) Hex colour overriding an unfocused pane’s border, e.g. #585b70.
session_colors bool true Give each session its own colour on the rail and in the switcher.
session_border bool false Carry the session’s colour on every pane border, not only on the rail.

theme empty means no theming: panes use your terminal’s own sixteen colours. border_focused_color and border_unfocused_color override only the border inks; they are not part of a theme file. See Themes and Glyph sets.

[appearance]
theme = "catppuccin_mocha"
glyphs = "unicode"
border_focused_color = "#89b4fa"
border_unfocused_color = "#45475a"
session_border = true      # carry each session's colour on every pane border

Backgrounds

Key Type Default Meaning
background string off Background painted on every surface not set on its own (panes, desktop, window chrome, dock, rail): off (your terminal shows through), theme, or a #RRGGBB literal. Values: off, theme.
pane_background string (empty) Background behind pane content: off, theme, or a #RRGGBB literal; empty follows appearance.background. Values: off, theme.
desktop_background string (empty) Background behind and between panes, including gaps and an empty workspace: off, theme, or a #RRGGBB literal; empty follows appearance.background. Values: off, theme.
window_chrome_background string (empty) Background under pane borders, title bars and the lines between shared-border panes: off, theme, or a #RRGGBB literal; empty follows appearance.background. Values: off, theme.
dock_background string (empty) Background under the dock: off, theme, or a #RRGGBB literal; empty follows appearance.background. Values: off, theme.
sidebar.background string (empty) Background under the rail: off, theme, or a #RRGGBB literal; empty follows appearance.background. Values: off, theme.

A cell with no background of its own is transparent, so your terminal’s own background shows through it. That is the default for every surface: pane content a program left on the default background, the gaps between panes, the borders, the dock and the rail. These six options paint those cells instead.

Value What is painted
off Nothing. Your terminal shows through.
theme The active theme’s background, with the theme’s foreground on default-coloured text. With no theme set it behaves as off, and the validator warns.
#RRGGBB That colour. With a theme, default-coloured text takes the theme’s foreground, lifted until it reads on the colour; with none, it keeps your terminal’s foreground.
empty (per surface only) Follow appearance.background.

A surface’s own option wins whenever it has a value, off included. A value that is neither a keyword nor a #RRGGBB literal resolves to off for that surface (it does not fall back to background), with a warning.

[appearance]
background = "theme"          # every surface on the theme's background
dock_background = "#11111b"   # the dock a shade darker
pane_background = "off"       # panes keep the terminal's own background

[appearance.sidebar]
background = "#181825"

Only cells with no background are painted. A background a program chose always wins, and so do tuios’s own marks: the selection, search matches, the copy-mode cursor, border inks, title-bar buttons, the dock’s pills and the rail’s highlighted rows. Overlay panels (palette, settings, which-key, Inbox, pickers, tooltips) fill their own rectangle and are not affected.

While the pane background paints a colour, a program’s OSC 11 query for the background is answered with that colour and OSC 10 with the text colour tuios gives default text there. See OSC colour queries.

Each workspace starts with these values. A layout key that changes a workspace on screen (such as resizing the master) is kept by that workspace, so these are starting points, not live bindings. With master_position = "center", the stack panes go to the right and the left in turn and master_grid has no effect. See Concepts for the three layouts.

[startup]
layout = "master-stack"

[appearance]
master_position = "center"   # an editor in the middle, terminals both sides

Sounds, cue files and quiet hours

tuios has two cues, not one per state, because two sounds can be told apart by ear in under half a second and a third would be guessed at:

Cue Plays for Character
attention (sounds.needs_input) needs_input, errored Higher, longer, louder
done (sounds.done) done, idle Quiet, informational

sound = true turns sound on. sound_mode decides what sound means:

sound_mode Effect
audio (default) Play the cue through a system audio player
bell Write a BEL and let your terminal decide (flash, sound, nothing)
both Do each

For audio, tuios uses the first player it finds, once per process:

Platform Players, in order
Linux, BSD paplay, pw-play, aplay -q, ffplay, mpv
macOS afplay, ffplay, mpv
Windows powershell or pwsh (System.Media.SoundPlayer), ffplay, mpv

A cue file is a path to a WAV file. A path that does not exist falls back to the built-in cue, so a typo costs the custom sound and not all sound. aplay and pw-play do not decode compressed formats, so use WAV for files that must play everywhere; afplay, ffplay and mpv also play MP3 and others.

  • Cooldown. sound_cooldown_seconds (default 3) is the shortest gap between two audio cues, across every pane, so six agents finishing together make one sound. The bell is not rate-limited by tuios.
  • One at a time. A single worker with a one-deep queue plays the cues, so cues never overlap.
  • No audio. A machine with no working player goes quiet for the life of the process after a run of failures, and prints nothing.
  • Where it plays. The cue plays where the client runs. Under tuios ssh and tuios-web that is the server, and tuios warns about it when the client starts; use sound_mode = "bell" to ring your own terminal. With tuios attach --host, the client runs on your machine.
  • Turn it all off. TUIOS_NO_SOUND=1 silences sound whatever the config says, for a test run, CI or a recording.

Quiet hours silence every sink: the notification, the dock message, the sound, the command and the after-agent-state hook. The value is one window, HH:MM-HH:MM, in the local time of the process that alerts. A window that wraps midnight, such as 23:00-07:00, is understood.

sound_mode = "both"
sound_cooldown_seconds = 5
quiet_hours = "23:00-07:00"

Custom theme files

A custom theme is a .json file directly in the themes directory (~/.config/tuios/themes/ on Linux; tuios list-themes prints the real path). Every file there is registered beside the built-ins at startup, so it is selected exactly like one. A file that does not parse is skipped with a warning, and the others still load.

The directory is read again on every tuios list-themes, and when an id that is not registered is selected with set-config. So you can write a file and select it without a restart. Selecting an id that is already registered does not re-read its file: to see an edit to a loaded theme, restart tuios or save it under a new id.

Light and dark

tuios decides whether a background is light or dark by its luminance, with hysteresis: a dark verdict turns light only above an 8-bit luminance of 140, and a light one turns dark only below 110, so a mid grey does not flip.

  • With a theme, the theme’s background decides. On a light theme the dialog ramp is built from the background (a dialog is a light panel, not a dark slab), accents are darkened just enough to read (4.5:1 for text, 3:1 for marks), and modal_dim fades toward the background instead of darkening.
  • With no theme, the host terminal’s background decides. When it starts or attaches, a client asks its terminal for its background, foreground and sixteen colours, and draws the chrome with the light ramp on a light terminal.
  • Following the system. A local client turns on mode 2031. A terminal that supports it (ghostty, kitty, contour and others) then reports switches between light and dark appearance; tuios asks for the colours again, tells the panes and redraws the chrome. SSH and browser clients ask once when they attach and do not follow the switch.
  • Terminals that do not answer (mosh, for example) leave the defaults: panes are told a black background and white text, and the chrome uses its dark ramp. Set a theme or pane_background to give panes a real answer.

There is no separate light and dark theme pair in v0.8.5: appearance.theme is one id. To switch with the system, call tuios set-config appearance.theme from a script that watches your desktop’s appearance.

Programs such as editors ask the terminal for its colours with OSC 10 (foreground), OSC 11 (background) and OSC 4 (palette entries) and pick a light or dark palette from the answer. tuios answers for each pane:

Situation OSC 11 / OSC 10 answer OSC 4 answer
The program set its own colours with OSC 10/11 Its own colours -
pane_background paints a colour That colour / the text colour tuios uses there Theme or host palette
A theme, pane background off The theme’s bg / fg The theme’s sixteen
No theme, pane background off The host terminal’s own colours The host terminal’s sixteen

Each client asks its own terminal, so an SSH client on a light terminal and a local client on a dark one each get the right answer while they are the one typing. In a daemon session the daemon’s emulator answers, using what the client told it at its last sync; with several clients, the last to sync decides.

# inside a pane: ask for the background (the reply arrives on the tty)
printf '\033]11;?\033\\'

Colour depth

The chrome is designed for each colour depth separately, and the depth is read the usual way:

Depth Detected when Chrome
truecolor COLORTERM=truecolor or 24bit, or a known terminal (kitty, ghostty, wezterm, alacritty, foot) The designed ramp
256 TERM ends in 256color with no COLORTERM (Apple Terminal, mosh, tmux without Tc) Greys from the xterm ramp 232-255; accents to the nearest palette entry in OKLab
16 TERM=xterm, TERM=linux, NO_COLOR No painted grounds; thin frame lines; reverse video for the selected row; colours are your palette’s slots

At 16 colours a theme’s chrome RGB values have no slot, so they give way to the slots their roles derive from. mosh 1.4 and later pass 24-bit colour but do not forward COLORTERM; set it on the remote side:

export COLORTERM=truecolor

Glyph sets

A theme decides what colour the chrome is; a glyph set decides what shape it is: the border corners, the window controls, rules and separators, and the marks on the rail. It is one option, appearance.glyphs, plus a JSON format for your own. Upstream reference: GLYPHS.md.

The built-in sets

Id What it is
default What tuios ships: rounded frame, Nerd Font powerline caps, ✕ and □ controls
unicode Box drawing and geometric shapes, with no Nerd Font private-use glyphs, for a good font that is not patched
heavy One stroke weight heavier throughout, border and junctions included
ascii Nothing outside 7-bit ASCII

Selecting a set

[appearance]

tuios list-glyphs                            # sets, roles, the active set, the directory
tuios list-glyphs heavy                      # role by role: what the set says, what draws
heavy  (Heavy)

   add                   -      +
   border.top_left       ┏      ┏

   focus                 █      █

On the settings page, the Glyph set row sits under Theme and opens a picker that previews each set live.

The border

A set may define a border, but the border that draws is whichever appearance.border_style names. glyphs is the style that means “the active set’s border”:

[appearance]
glyphs = "heavy"
border_style = "glyphs"

A set that names only some border runes gets the rounded border for the rest, so “square corners, everything else as usual” is four lines.

Roles

Group Roles
Window controls close, maximize, minimize, dot (traffic-light disc), pill_left, pill_right
Rules and separators rule (hairline), separator (dock gap), arrow_left, arrow_right (overflow chevrons)
Rail marks focus, attention, bullet, add, collapse, expand, tree_branch, tree_last, fold_open, fold_shut
Files section folder, parent (the .. row), file (drawn when file icons are off or in ASCII mode)
Scrollbar scrollbar_thumb, scrollbar_track
Text ellipsis, sigil, dash_rule
Border (border object) top, bottom, left, right, top_left, top_right, bottom_left, bottom_right, middle, middle_top, middle_bottom, middle_left, middle_right

Most roles must be exactly one cell wide. A glyph of the wrong width is dropped back to the default and reported under problems, because the window controls’ click targets are fixed offsets. separator, ellipsis, collapse and expand may be any width. Border runes must be one cell.

Writing a set

Write ID.json in the glyphs directory (the path tuios list-glyphs prints). Every field is optional:

Key Meaning
id The set’s id; default is the file name
display_name Name shown in the picker
inherits A set to start from, usually a built-in; followed up to eight levels, a loop stops
any role name The glyph for that role
border An object with the border roles

A role you leave out keeps what the inherited set says, falling through to what tuios ships. The directory is read again whenever a set is looked up, so a new file is selectable at once. Saved as square-heavy.json, this set has the id square-heavy:

{
  "display_name": "Square Heavy",
  "inherits": "heavy",
  "bullet": "◦",
  "focus": "▐",
  "attention": "▲",
  "close": "x",
  "separator": " │ ",
  "ellipsis": "…",
  "border": {
    "top_left": "┏",
    "top_right": "┓",
    "bottom_left": "┗",
    "bottom_right": "┛"
  }
}
tuios set-config appearance.glyphs square-heavy
tuios set-config appearance.border_style glyphs
tuios list-glyphs square-heavy --json | jq -r '.problems[]?'
glyph set mine: close is 2 cells wide and the layout budgets 1, so it keeps the default

That line is what a problem looks like. problems is present only when there are any, so an empty result means every role drew.

What the terminal can draw

When the config names no glyph set and --ascii-only is not given, each local client reads its environment when it starts:

  • A locale that is not UTF-8. The first of LC_ALL, LC_CTYPE and LANG that is set decides. A value such as C, POSIX or en_US.ISO-8859-1 makes tuios run as if --ascii-only were given. None of the three set at all is not read as the C locale.
  • TERM=linux. The Linux console has box drawing and no Nerd Font icons, so the chrome takes the unicode set and the dock, notification and context-menu icons take their ASCII forms.

A glyph set in the config, or --ascii-only, always wins. tuios list-glyphs says what the terminal it runs in would pick and why. Clients served by tuios ssh and tuios-web are not detected this way, since the server’s environment says nothing about the remote terminal.

ASCII mode

--ascii-only says the terminal cannot draw beyond 7-bit ASCII. It overrides a glyph set per role: a set keeps each role it spelled in ASCII and gives up the rest. It also replaces the dock’s semantic icons (the mode chip, the counts, the session controls), which no glyph set can change.

tuios --ascii-only
tuios list-glyphs ascii --json | jq .set.ascii    # true: drawable anywhere

The upstream glyph documentation mentions an ascii_only config key, but the v0.8.5 config struct has no such field. Use the --ascii-only flag, or glyphs = "ascii" for the shapes alone.

Hooks

A hook runs a shell command when something happens, with TUIOS_* environment variables carrying the facts. Hooks are configured in [hooks] and are not in the registry. Upstream reference: HOOKS.md.

The table

Each event takes one command or a list of commands, each run with sh -c:

[hooks]
after-new-window  = "notify-send 'tuios' \"new window $TUIOS_WINDOW_NAME\""
after-agent-state = ["sh ~/.config/tuios/hooks/phone.sh", "tuios refresh-dock agents"]

Events

Event Fires when Runs in Fires with nobody attached
after-new-window A window is created daemon yes
after-close-window A window is closed daemon yes
after-focus-change The focused window changes daemon yes
after-workspace-switch The current workspace changes daemon yes
after-agent-state A pane’s agent state changes, for the transitions [notifications.agent] alerts on daemon yes
after-command-finished A pane’s shell reports a finished command through OSC 133 marks daemon yes
after-attach This client attaches client no
after-detach This client detaches client no
after-resize This client’s terminal is resized client no
after-layout-change The layout the client computes changes client no

A daemon hook fires once however many clients are attached; a client hook fires once per client (three clients attaching is three attaches). A tuios with no daemon runs every hook itself, except after-command-finished, which only the daemon can follow.

after-agent-state follows the alert policy: only the states in [notifications.agent.states] (needs_input, errored and done by default), after settle_seconds, outside quiet_hours, and not for the pane an attached client is showing while suppress_focused is on. When every attached client’s terminal has reported losing focus, nobody counts as looking, and the hook fires for the shown pane too (tuios session-info shows this as host focus).

Environment

Every hook gets every variable. One that does not describe the event is empty, or 0 for a number:

Variable Holds Set for
TUIOS_EVENT The event name all
TUIOS_SESSION_ID The session’s name all
TUIOS_WINDOW_ID The window’s id window and agent events
TUIOS_WINDOW_NAME The window’s name window and agent events
TUIOS_WORKSPACE The workspace number all that have one
TUIOS_PREV_WORKSPACE The workspace before the switch after-workspace-switch
TUIOS_LAYOUT The layout after the change after-layout-change
TUIOS_WIDTH, TUIOS_HEIGHT The size after the change after-resize
TUIOS_AGENT_STATE, TUIOS_AGENT_PREV_STATE The state moved to and from after-agent-state
TUIOS_AGENT_HARNESS The harness, such as claude-code after-agent-state
TUIOS_AGENT_MESSAGE The message that came with the state after-agent-state
TUIOS_COMMAND The command line, cut to 512 bytes, likely secrets masked after-command-finished
TUIOS_EXIT_CODE The exit status; empty when the shell sent none after-command-finished
TUIOS_DURATION_MS How long it ran, in milliseconds after-command-finished

A daemon hook runs with the daemon’s environment, not your current shell’s. A daemon started by tuios new keeps the environment of that first shell. Use full paths to programs when in doubt. TUIOS_AGENT_MESSAGE is the agent’s own text: think before a hook sends it off the machine.

When hooks are read

The daemon reads [hooks] when it starts and does not reload it. After you change a daemon hook, restart the daemon:

tuios kill-server     # ends every session; saved sessions are restored on the next start
tuios

Client hooks are read when the client starts, so detach and attach again.

Five example hooks

Example: a phone alert when an agent needs you

The daemon runs after-agent-state with nobody attached, so this reaches you away from the desk. It sends the pane’s name and state, not its message.

#!/bin/sh
# ~/.config/tuios/hooks/phone.sh
curl -s -m 5 -H "Title: tuios: $TUIOS_AGENT_STATE" \
  -d "$TUIOS_SESSION_ID/$TUIOS_WINDOW_NAME is $TUIOS_AGENT_STATE" \
  https://ntfy.sh/your-private-topic > /dev/null
[hooks]
after-agent-state = ["sh ~/.config/tuios/hooks/phone.sh"]

[notifications.agent]
suppress_focused = true
quiet_hours = "23:00-07:00"

Example: tell me when a long command fails

after-command-finished needs shell integration that sends OSC 133 marks (tuios doctor shell says which panes have it). This notifies only for commands that ran over a minute and exited non-zero.

#!/bin/sh
# ~/.config/tuios/hooks/long-fail.sh
[ -n "$TUIOS_EXIT_CODE" ] || exit 0
[ "$TUIOS_EXIT_CODE" -ne 0 ] || exit 0
[ "${TUIOS_DURATION_MS:-0}" -ge 60000 ] || exit 0
secs=$((TUIOS_DURATION_MS / 1000))
msg="exit $TUIOS_EXIT_CODE after ${secs}s: $TUIOS_COMMAND"
if command -v osascript >/dev/null 2>&1; then
  osascript -e "display notification \"$msg\" with title \"tuios $TUIOS_WINDOW_NAME\""
else
  notify-send "tuios $TUIOS_WINDOW_NAME" "$msg"
fi
[hooks]
after-command-finished = "sh ~/.config/tuios/hooks/long-fail.sh"

Example: keep a dock cell current without polling

A custom component with refresh = "once" runs only when asked, and a hook asks at exactly the right moment.

[dock]
right = ["notifications", "copy-help", "custom/agents", "clock", "session-controls"]

[dock.custom.agents]
command = "~/.config/tuios/dock/agents.sh"
refresh = "once"

[hooks]
after-agent-state = "tuios refresh-dock agents"
after-close-window = "tuios refresh-dock agents"

Example: a time log of workspace switches

Each line records when you moved between workspaces, for a later report.

[hooks]
after-workspace-switch = '''printf '%s\t%s\t%s\t%s\n' "$(date +%FT%T)" "$TUIOS_SESSION_ID" "$TUIOS_PREV_WORKSPACE" "$TUIOS_WORKSPACE" >> ~/.local/state/tuios-workspaces.tsv'''
# how many times each workspace was switched to
awk -F'\t' '{print $4}' ~/.local/state/tuios-workspaces.tsv | sort | uniq -c

Example: a status file for a desktop bar

Client hooks run in the client, so they act on the machine you sit at. This keeps a file a desktop bar (waybar, SketchyBar) can read. Only after-resize carries the size; the other two leave TUIOS_WIDTH and TUIOS_HEIGHT at 0.

[hooks]
after-attach = "echo \"attached $TUIOS_SESSION_ID\" > ~/.cache/tuios-status"
after-detach = "echo detached > ~/.cache/tuios-status"
after-resize = "echo \"attached $TUIOS_SESSION_ID ${TUIOS_WIDTH}x${TUIOS_HEIGHT}\" > ~/.cache/tuios-status"

When a hook does not fire

tuios list-hooks
tuios list-hooks --event after-agent-state
tuios list-hooks --json | jq '.hooks[] | select(.last_error != "")'

list-hooks lists every registered command with its side, how many times it ran, its last exit code, when it last ran and its last error. Client hooks are listed only while a client is attached.

What you see What it means
No row The hook was never loaded: check the event name, and restart the daemon for a daemon hook
RUNS is 0 The command is registered and the event never happened
Non-zero exit The command ran and failed; the error says why

The daemon also logs a warning for every failing hook, with the exit code and the last 1 KiB of stderr. tuios daemon --log-level=basic adds one line per firing.

Glossary

Chrome
Everything tuios draws itself: borders, title bars, the dock, the rail and overlay panels. A theme colours it and a glyph set shapes it.
Cue
One of the two alert sounds, attention or done. A cue file replaces one.
Daemon hook
A hook the daemon runs. It fires with nobody attached and needs a daemon restart to reload.
Dock
The bar at the top or bottom of the screen, made of components in three regions.
Glyph set
A named set of characters for the chrome’s roles, built in or a JSON file in glyphs/.
Option registry
The list of every scalar config path, with type, default and accepted values, shared by list-options, get-config, set-config and the settings page.
Quiet hours
A daily local-time window during which agent and mail alerts are silent.
Rail
The sidebar of sessions, terminals, files and agents, configured in [appearance.sidebar].
Role
One place a glyph set can fill, such as close, focus or border.top_left.
Surface
A region a background option can paint: panes, desktop, window chrome, dock, rail. Also the base grey of the dialog ramp in a theme’s chrome.
Theme
Sixteen ANSI colours plus foreground, background and cursor, and optional chrome colours, built in or a JSON file in themes/.
